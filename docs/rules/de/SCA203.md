# SCA203 — for-Schleife läuft einen Index über das Ende

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> for-Schleife läuft bis Count, Length() oder High() + 1 und indiziert dieselbe Sammlung mit der Schleifenvariablen - der letzte Durchlauf liegt außerhalb

## Beschreibung

Ein klassischer Off-by-one-Fehler: 'for i := 0 to List.Count do' mit List[i] im Rumpf liest List[List.Count], ein Element hinter dem Ende. Der Compiler akzeptiert das; zur Laufzeit löst es mit {$R+} ERangeError aus, bei TList und TStrings EArgumentOutOfRangeException oder EStringListError, und andernfalls liest oder schreibt es stillschweigend den Speicher hinter dem letzten Element. Gemeldet werden Schleifenköpfe, deren Obergrenze einen Index zu weit reicht - 'X.Count' (ab 0, oder ab 1, wenn X eine nachgewiesene Liste ist), 'Length(A)' ab 0, 'Low(A) to Length(A)' bei einem dynamischen Array, 'High(A) + 1' -, wenn der Rumpf dieselbe Sammlung (gleicher Name oder gleiche Kette) mit der unverschobenen Schleifenvariablen liest oder schreibt: X[i], X[i, j] und bei .Count auch X.Items[i], X.Strings[i] und X.Objects[i]. Strings sind 1-basiert und haben eigene Formen: '0 to Length(S)' mit S[i] ist an beiden Enden falsch (S[0] vor dem ersten Zeichen), '1 to Length(S) + 1' hinter dem letzten; '1 to Length(S)' ist korrekt. Der Fund ist nur dann ein Fehler, wenn der Typ nachgewiesen ist: Die Sammlung ist ein in der Unit deklarierter Name (Parameter, lokale oder Inline-Variable, Result, Feld der eigenen Klasse der Methode oder ihrer Vorfahren in der Unit, Unit-Variable), dessen Typ eine bekannte Liste (TList, TObjectList, TStrings, TStringList, TCollection, TMenuItem, FPC TFPList/TFPGList ...), ein Array oder ein String ist, und der Rumpf verlässt den Durchlauf weder vor dem Zugriff (break, exit, continue, raise, goto), noch vergrößert er die Sammlung, noch enthält er eine anonyme Methode. Andernfalls ist er eine Warnung. Behebung: Count - 1, High(A) (oder Length(A) - 1) und bei Strings 1 to Length(S).

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
for i := 0 to Names.Count do
  WriteLn(Names[i]);   // Names[Names.Count] raises
```

### Gut (idiomatische Korrektur)

```pascal
for i := 0 to Names.Count - 1 do
  WriteLn(Names[i]);
```

## Absichtlich nicht gemeldet

Bei den folgenden Konstrukten schweigt der Detektor absichtlich. Jedes davon ist eine False-Positive-Klasse, die am Realwelt-Korpus gemessen wurde — keine Vermutung.

### Shifted index, insert position, other collection

Only an access with the plain loop variable proves the last pass is out of range. X[i - 1] with '1 to X.Count', X.Insert(i, ..) (valid up to Count) and an index into another collection (M[i] while counting L, X.L[i] while counting L) are correct or not decidable lexically.

```pascal
for i := 1 to L.Count do S := L[i - 1];  // not reported
```

### A guard on the loop variable

When an if, while, case or until condition in the body before or with the first access names the loop variable outside the index (if i < L.Count, if i = Length(A) then .. else A[i]), the extra pass is deliberate - typically a sentinel step after the last element.

```pascal
for i := 0 to Length(A) do if i = Length(A) then Flush else Add(A[i]);  // not reported
```

### Forms that are correct without a type proof

'1 to X.Count' is not reported for an unproven X: COM collections such as Excel's Sheets are 1-based. 'Low(A) to Length(A)' is reported only for a dynamic array: for a static 'array[1..N]' and for a string it is correct. '1 to Length(S) + 1' needs a proven string. ShortString and PChar are not reported for Length: S[0] is the length byte and P[Length(P)] the terminating #0. For TDictionary-like types X[i] is a key, not a position.

```pascal
for i := 1 to Sheets.Count do Sheets[i].Calculate;  // not reported
```

### Known limits

The loop variable assigned in the body vetoes the finding. downto loops, bounds with further arithmetic (Count - 1, Pred(Count)), named indexed properties other than Items, Strings and Objects (RTID.ThreadIDs[i] while counting RTID.Count) and accesses through 'with' are not reported.

```pascal
for i := 0 to RTID.Count do TID := RTID.ThreadIDs[i];  // not reported (false negative)
```
