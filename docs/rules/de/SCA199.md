# SCA199 — ParamByName-Name passt nicht zu den SQL-Platzhaltern

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> ParamByName('x') an einer Query, deren SQL kein :x hat (zur Laufzeit 'Parameter nicht gefunden'), oder ein :y im SQL, das die Routine nie zuweist, obwohl sie die anderen Parameter der Query setzt

## Beschreibung

Der Compiler sieht die Verbindung zwischen Query.SQL und Query.ParamByName nicht - beides sind Strings. Ein umbenannter Platzhalter, ein Tippfehler oder ein kopierter Block hinterlässt ein ParamByName, dessen Name nicht im SQL steht, und der Fehler zeigt sich erst, wenn die Anweisung ausgeführt wird: FireDAC, BDE, dbExpress, UniDAC, Zeos und ADO (Parameters.ParamByName) lösen alle 'parameter not found' aus. Die Gegenrichtung wird für Queries gemeldet, die die Routine selbst erzeugt: Das SQL hat :y, die Routine bindet andere Parameter dieser Query, aber nie y - die Ausführung scheitert dann an einem ungebundenen Parameter (FireDAC: unbekannter Datentyp, Oracle: ORA-01008) oder bindet stillschweigend NULL. Die Prüfung arbeitet je Routine und je Query-Variable, liest ab dem ersten 'begin' der Routine und nur dann, wenn sie das SQL der Query vollständig aus Literalen in dieser Routine kennt: Die Query wird dort erzeugt (Q := TXxx.Create) oder ihr SQL wird vor dem ersten Add geleert oder zugewiesen, und jeder Beitrag ist ein String-Literal (sLineBreak und #13#10 eingeschlossen). Platzhalter sind :name außerhalb von SQL-Strings und -Kommentaren - auch :@name (ADO, SQL Server), Namen mit $ oder # (Oracle) und :"Namen in Anführungszeichen" -, und ein Name gilt als vorhanden, wenn er entweder zur Bezeichner-Lesart passt oder zur Lesart von Data.DB/ADODB ParseSQL, die bis zum nächsten Leerzeichen, Komma, Semikolon oder zur schließenden Klammer reicht; für die Richtung unbekannter Name zählt auch ein Platzhalter in einem SQL-Kommentar als vorhanden, weil Data.DB, ADO und IBX ihn trotzdem anlegen. '::'-Typecasts, ':=' (PL/SQL), positionales ':1', ':new.'/':old.' in Trigger-Rümpfen und '?'-Parameter sind keine Namen. Namen werden ohne Beachtung der Groß-/Kleinschreibung verglichen, wie es alle Bibliotheken tun. Als Binden zählen die Zugriffe: ParamByName, Params.ParamByName, Parameters.ParamByName, FindParam, ParamValues['a;b'] und für Direct Oracle Access SetVariable, DeclareVariable, SetComplexVariable, SetLongVariable.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
Q := TFDQuery.Create(nil);
Q.SQL.Add('SELECT name FROM customer');
Q.SQL.Add('WHERE customer_id = :customer_id');
Q.ParamByName('custid').AsInteger := Id;   // no :custid - raises at Open
Q.Open;
```

### Gut (idiomatische Korrektur)

```pascal
Q := TFDQuery.Create(nil);
Q.SQL.Add('SELECT name FROM customer');
Q.SQL.Add('WHERE customer_id = :customer_id');
Q.ParamByName('customer_id').AsInteger := Id;
Q.Open;
```

## Absichtlich nicht gemeldet

Bei den folgenden Konstrukten schweigt der Detektor absichtlich. Jedes davon ist eine False-Positive-Klasse, die am Realwelt-Korpus gemessen wurde — keine Vermutung.

### SQL not fully known in the routine

Add without a preceding Create, SQL.Clear or SQL.Text := appends to SQL that comes from the DFM or another routine. Format(), variables, constants, SQL.Assign, LoadFromFile, macros (MacroByName), Open/ExecSQL with an SQL argument and a string literal in the SQL that does not close (Oracle q-quotes are understood, backslash escapes are not) hide parts of the text. In all these cases the rule stays silent - a placeholder it cannot see would turn a correct ParamByName into a false report.

```pascal
qryUser.SQL.Add('AND active = :active');  // rest of the SQL in the DFM - not reported
```

### The query leaves the routine's view

A query passed as a value (BindParams(Q), Result := Q, DataSource.DataSet := Q), a query on which an unknown method with arguments runs (Q.AddWhere('...')), a query mentioned in a nested routine, and a query that is not created in the routine while the routine calls an own method without arguments (BindFilter;) are not judged: any of these may change its SQL or bind its parameters out of sight. FreeAndNil/Assigned and dataset methods such as FieldByName, Locate, First or Close do not count.

```pascal
Q.SQL.Text := 'select ... where a = :a'; AddFilter(Q);  // not reported
```

### Unclear target

A routine with a 'with' statement, with SQL/ParamByName without an object in front, or behind a cast or index (TFDQuery(X).SQL, Queries[i].SQL) is skipped as a whole: which query an access belongs to is not certain lexically.

```pascal
with Q do ParamByName('x').AsString := S;  // not reported
```

### Unassigned placeholder on a query the routine does not create

The second direction (placeholder without assignment) is reported only for queries created in the routine. A form field or DFM query gets parameters from master-detail links (MasterSource/DataSource), from DFM Params or from other routines. It is also suppressed when Params are touched dynamically (Params[i], ParamByName(Variable), MasterSource :=) and when the SQL is a program block (BEGIN ... END, Firebird EXECUTE BLOCK, PL/SQL), where ':v' may be a local variable.

```pascal
qryOrders.SQL.Text := 'select ... where cust = :cust and y = :y'; qryOrders.ParamByName('y')...  // :cust from the master - not reported
```

### FindParam and Direct Oracle Access

FindParam returns nil instead of raising, and whether DOA rejects a declared variable that is missing from the SQL is not established here. Both count as binding for the second direction but are not reported as unknown names.

```pascal
Q.FindParam('legacy');  // not reported
```

### Alternative SQL texts

All SQL a routine gives a query is read as one text, including Clear/Text := resets and conditional branches. A ParamByName that matches any of the alternatives is accepted - a ParamByName aimed at an earlier statement after the SQL was replaced is a false negative on purpose.

```pascal
if A then Q.SQL.Text := '... :a' else Q.SQL.Text := '... :b';  // ParamByName('a') accepted
```
