# SCA139 — Free ohne anschließendes nil-Setzen

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Code%20Smell-yellow)

> `obj.Free;` ohne `obj := nil;` (oder ohne FreeAndNil) hinterlässt einen hängenden Zeiger - jede weitere Verwendung ist ein Use-After-Free

## Beschreibung

Nach `obj.Free` zeigt die Variable weiterhin auf den freigegebenen Speicher. Jede weitere Dereferenzierung ist Use-After-Free, bestenfalls eine Access Violation, schlimmstenfalls stille Korruption. Der Detektor durchläuft `nkCall`-Knoten, deren Name `<ident>.Free` oder `<ident>.Destroy` entspricht, und durchsucht dann dieselbe Methode vorwärts nach einem folgenden `<ident> := nil` oder `FreeAndNil(<ident>)`. Fehlt beides, wird der Aufruf gemeldet - in einer Methode auch, wenn er der letzte Aufruf ist: Ein Feld überlebt die Methode, und eine spätere `Assigned`-Prüfung oder der Destruktor berührt freigegebenen Speicher (in einem Konstruktor führt Delphi bei jeder Ausnahme den Destruktor aus). Eine eigenständige Routine, die als letzten Aufruf eine globale Variable freigibt (Aufräumen am Programm- oder Skriptende), wird nicht gemeldet, außer es folgt ein `raise`. Lokale Variablen, Inline-Konstanten und `const`-Parameter werden übersprungen (sie verlassen den Gültigkeitsbereich), ebenso Destruktoren, `BeforeDestruction`, `DoFree`, `FinalizeClass`, OnDestroy-Handler und eigenständige `Finalize*`-Routinen (mit ihnen endet die Instanz, die Klasse oder das Programm). `Self`/`Result`/`inherited` als Empfänger sind ausgenommen, da sie anderen Lebenszyklusmustern folgen. Entspricht Sonar-50-Regel #25.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  L.Free;             // <- L still points at freed memory
end;
WriteLn(L.Count);     // Use-After-Free
```

### Gut (idiomatische Korrektur)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  FreeAndNil(L);      // L is nil; further use raises loudly
end;
```
