# SCA108 — TThread.Synchronize aus dem Destruktor

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> Synchronize() aus dem Destruktor Destroy gerufen - ein sich selbst freigebender Thread blockiert dort, bis der Hauptthread den Aufruf ausführt, und hängt, wenn er es nicht tut

## Beschreibung

TThread.Synchronize() in einem Destruktor-Rumpf ist fragil. Läuft der Destruktor im Hauptthread, ruft Synchronize die Methode einfach direkt auf. Läuft er im Worker-Thread selbst - der übliche Fall bei FreeOnTerminate := True, wo sich der Thread nach Execute selbst freigibt -, blockiert Synchronize den Worker, bis der Hauptthread den Aufruf ausführt. Bearbeitet der Hauptthread in diesem Moment keine Synchronize-Anfragen (etwa weil er mit WaitForSingleObject statt TThread.WaitFor auf den Thread wartet oder weil die Anwendung gerade beendet wird), warten beide Threads aufeinander und der Prozess hängt. Beim Beenden können die Objekte, die der Aufruf berührt, zudem schon weg sein. Die Benachrichtigung in einen OnTerminate-Handler verlegen (er läuft im Hauptthread, bevor das Thread-Objekt freigegeben wird) oder ans Ende von Execute. AST-basiert: durchläuft jede nkMethod, deren Name auf '.Destroy' endet (oder deren TypeRef den Marker 'destructor' trägt), und meldet nkCall auf 'Synchronize' / '<obj>.Synchronize'.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
destructor TWorker.Destroy;
begin
  Synchronize(procedure begin Form1.Log('done') end);  // worker blocks until the main thread runs this
  inherited;
end;
```

### Gut (idiomatische Korrektur)

```pascal
procedure TWorker.WorkerTerminated(Sender: TObject);  // in the constructor:
begin                                                 //   OnTerminate := WorkerTerminated;
  Form1.Log('done');   // OnTerminate runs in the main thread, before Destroy
end;

destructor TWorker.Destroy;
begin
  inherited;   // no Synchronize here
end;
```
