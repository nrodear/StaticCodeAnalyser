## Beschreibung

Eine leere Methode kann auf eine vergessene Implementierung hinweisen, auf ein nie weiterverfolgtes TODO oder auf einen Interface-Stub. Die Absicht explizit machen (assert, Ausnahme oder Kommentar). Nicht gemeldet: ein leerer Rumpf, der bereits einen erklärenden Kommentar trägt ({ do nothing }, // default implementation does nothing) - das *ist* eine der drei Korrekturen, die die Regel verlangt. Nicht als Absicht gezählt: Compiler-Direktiven ({$REGION}, {$IFDEF}) und auskommentierter Code (erkannt am abschließenden Semikolon). Das schwächt die Projektregel nicht ab, dass Kommentare nie als Code-*Verwendung* zählen - hier geht es um dokumentierte Absicht, nicht um Verwendung.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
procedure DoStuff;
begin
end;
```

### Gut (idiomatische Korrektur)

```pascal
procedure DoStuff;
begin
  raise ENotImplemented.Create('...');
end;
```

## Absichtlich nicht gemeldet

Bei den folgenden Konstrukten schweigt der Detektor absichtlich. Jedes davon ist eine False-Positive-Klasse, die am Realwelt-Korpus gemessen wurde — keine Vermutung.

### Empty body carrying an explanatory comment

The rule's own advice is to make the intent explicit by assert, exception *or comment*. A body that already carries a comment has followed that advice, so reporting it contradicts the fix the rule asks for. Two things do NOT count as intent: a compiler directive (`{$REGION}`, `{$IFDEF}`) is tooling rather than a statement about intent, and commented-out code - recognised by the trailing semicolon - documents nothing. Note this does not weaken the project rule that comments never count as code *usage*; the question here is documented intent, not use.

```pascal
// not reported - the intent is stated
procedure TFoo.DoNothing;
begin
  { do nothing - base class hook }
end;

// still reported - nothing says why
procedure TFoo.DoNothing;
begin
end;
```
