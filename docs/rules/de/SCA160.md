# SCA160 — String-Typecast aus einem rohen Zeiger

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> `string(P)` und Verwandte aus einem P-präfixierten Zeiger setzen einen Nullterminator voraus, den es nicht geben muss - Überlesen des Heaps

## Beschreibung

Lexikalischer Scan nach `(string|RawByteString|AnsiString|UTF8String|WideString)(<id>)`, wobei `<id>` mit `P` gefolgt von einem weiteren Buchstaben beginnt (Delphi-P-Präfix-Konvention für Zeigertypen: PByte, PChar, PSomeRecord, ...). Der Abgleich ignoriert Groß-/Kleinschreibung, daher trifft auch `pText`; ein Operand, der in derselben Datei mit einem String-Typ deklariert ist, wird übersprungen. Delphi behandelt den Typecast als nullterminiert und liest Speicher bis zum nächsten #0 - bei einem Puffer ohne Terminator läuft das über die Grenze des Heap-Blocks hinaus und führt zu stillem Überlesen und gelegentlicher AV. mORMot-Interna nutzen dieses Muster mit kontrollierter Nullterminierung; Anwendercode, der das Idiom kopiert, lässt die Terminator-Garantie oft weg. Stattdessen `SetString(s, PChar(Buf), Len)` mit expliziter Länge verwenden. Fehlalarm-Filter: Nur Bezeichner, die mit P beginnen, lösen aus - `string(IntegerVar)` (Integer-zu-String) wird nicht gemeldet; ein doppelter Typecast wie `string(PChar(x))` ebenfalls nicht.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
PText := PChar(Buf);
s := string(PText);   // reads up to the next #0 - overread if Buf has no terminator
```

### Gut (idiomatische Korrektur)

```pascal
SetString(s, PChar(Buf), Len);   // explicit length, no terminator needed
```
