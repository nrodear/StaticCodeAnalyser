# SCA146 — Boolean-Parameter als interner Verzweigungsschalter

![Severity](https://img.shields.io/badge/severity-Hint-blue) ![Type](https://img.shields.io/badge/type-Code%20Smell-yellow)

> Ein Boolean-Parameter, dessen Wert zwischen zwei völlig verschiedenen Codepfaden wählt, ist eine verdeckte Strategie - besser zwei Methoden mit sprechenden Namen

## Beschreibung

Wenn der Wert eines Boolean-Parameters die Funktion zwischen zwei unabhängigen Verhaltensweisen umschaltet (`SendMsg(s, True)` vs. `SendMsg(s, False)`), ist die Aufrufstelle undurchsichtig: Der Leser muss entweder die API der Methode im Kopf haben oder nachschlagen, um zu wissen, was `True` bedeutet. Zwei Methoden mit sprechenden Namen (`SendErrorMessage` / `SendInfoMessage`) machen die Absicht an der Aufrufstelle ohne Kommentare deutlich. Der Detektor durchläuft `nkMethod`-Knoten, sucht unter den `nkParam`-Kindern nach Boolean (auch LongBool/WordBool/ByteBool) und meldet, wenn mindestens ein `nkIfStmt` im Rumpf den Parameter als Bedingung verwendet. Ausgenommen: Property-Setter (Methodennamen, die mit `Set` beginnen), bekannte Parameternamen von VCL-Event-Handlern (`Handled`, `CanShow`). Reines Durchreichen (Bool nur weitergegeben, ohne interne Verzweigung) wird nicht gemeldet. Entspricht Sonar-50-Regel #33. Schweregrad Hinweis - dies ist ein Refactoring-Vorschlag, kein Bug.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
procedure SendNotification(const Msg: string; IsError: Boolean);
begin
  if IsError then Notify(Msg, clRed) else Notify(Msg, clBlack);
end;
// Caller: SendNotification(s, True);     // True = ???
```

### Gut (idiomatische Korrektur)

```pascal
procedure SendErrorNotification(const Msg: string);
begin Notify(Msg, clRed); end;

procedure SendInfoNotification(const Msg: string);
begin Notify(Msg, clBlack); end;
// Caller: SendErrorNotification(s);
```
