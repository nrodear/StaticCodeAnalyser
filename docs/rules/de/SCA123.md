# SCA123 — Typumwandlung direkt vor Free / Destroy

> `TFoo(x).Free` - die Typumwandlung beeinflusst nicht, welches Destroy läuft (Destroy ist virtuell)

## Beschreibung

`TStringList(L).Free` oder `TObject(L).Destroy` zu schreiben ist ein Verwirrungs-Smell. `TObject.Free` ist ein nicht virtueller Wrapper um das *virtuelle* `Destroy`, daher erfolgt der virtuelle Dispatch über den Laufzeittyp von `L`, nicht über den statischen Zieltyp des Typecasts. Ob `L.Free` oder `T(L).Free` geschrieben wird - es läuft dieselbe Destruktorkette. Der Typecast ist daher entweder überflüssig (Typecast auf den eigenen Typ der Variablen) oder irreführend (Typecast auf eine fremde Klasse, der nahelegt, Destroy wähle ein anderes Override - das tut es nicht). Ist das Ziel des Typecasts falsch, kann sich der umgebende Code auf diese falsche Annahme stützen und bei Refactorings brechen. Der Detektor gleicht `nkCall.Name` mit den Mustern `<Ident>(<expr>).Free[()][;]` und `<Ident>(<expr>).Destroy[()][;]` ab, wobei `<Ident>` der Delphi-Namenskonvention für Klassen/Interfaces folgt (`T` oder `I` plus Großbuchstabe). Einfaches `L.Free` und qualifiziertes `Owner.Bar(x).Free` (vermutlich Free auf einem Funktionsergebnis) werden nicht gemeldet. Entspricht Sonar-Delphi `CastAndFreeCheck`.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
procedure Cleanup(L: TObject);
begin
  TStringList(L).Free;     // cast has no effect on dispatch
end;
```

### Gut (idiomatische Korrektur)

```pascal
procedure Cleanup(L: TObject);
begin
  L.Free;                  // virtual Destroy resolves at runtime
end;
```
