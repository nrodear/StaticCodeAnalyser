# SCA202 — not, and, or oder xor bindet vor dem Vergleich

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

## Beschreibung

In Pascal binden die Operatoren not, and, or und xor stärker als die Vergleiche (=, <>, <, >, <=, >=, in) - in Delphi wie in Free Pascal. Zwei Schreibweisen kompilieren daher ohne Meldung und prüfen etwas anderes, als sie sich lesen. (1) 'not' vor einem Vergleich: 'if not List.Count > 0' ist '(not List.Count) > 0'. Bei einem Integer ist not das bitweise Komplement, daher ist die Bedingung für jedes Count >= 0 falsch; 'not Key in [...]' und 'not Result = mrOk' scheitern auf dieselbe Weise. (2) Mit and/or/xor verkettete Vergleiche: 'if A = True or B = False' ist '(A = (True or B)) = False'. Das kompiliert nur, wenn die Operanden Boolean (oder Variant) sind - bei Integern, Strings, Aufzählungen oder Mengen meldet der Compiler bereits einen Typfehler. Den Vergleich in Klammern schreiben: 'not (List.Count > 0)', '(A = True) or (B = False)' - oder den Vergleich mit True/False weglassen. Der Schweregrad ist Fehler, wenn der Typ belegt ist (eine Zahl oder eine Menge von Zahlen rechts, Pos/Ord/Length/CompareText... oder .Count/.IndexOf als Operand, eine lokale Variable, ein Parameter oder ein Feld eines Integer-Typs, True/False in der Kette), andernfalls Warnung. Gelesen werden Bedingungen von if/while/until/case und rechte Seiten von :=; Kommentare, String-Literale (auch mehrzeilige Strings von Delphi 12) und asm-Blöcke zählen nie als Code.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
if not List.Count > 0 then   // (not List.Count) > 0 - false for every Count
  Exit;
if Ready = True or Busy = False then   // (Ready = (True or Busy)) = False
  Start;
```

### Gut (idiomatische Korrektur)

```pascal
if not (List.Count > 0) then
  Exit;
if Ready or not Busy then
  Start;
```

## Absichtlich nicht gemeldet

Bei den folgenden Konstrukten schweigt der Detektor absichtlich. Jedes davon ist eine False-Positive-Klasse, die am Realwelt-Korpus gemessen wurde — keine Vermutung.

### Boolean operand with = or <>

For Boolean values (not A) = B is the same as not (A = B), so the order does not change the result. Not reported when True/False stands on the right, when the operand ends in a well-known Boolean member (Checked, Visible, Enabled, Active, ReadOnly, Modified, Focused, Showing, Eof, Bof, IsEmpty, Selected, Expanded, Down), or when the operand or the identifier on the right is a variable, parameter or field of a Boolean type. With <, >, <=, >= or in the order would matter for Booleans too - such code is practically never written and is not reported (deliberate false negative).

```pascal
if not CheckBox1.Checked = Ini.ReadBool('a', 'b', False) then  // not reported
```

### Bit tests and open intent

'Flags and Mask = 0' is '(Flags and Mask) = 0' - the correct bit test. 'not' behind and/or/* is part of the operand ('Flags and not Mask <> 0' clears bits before the test). 'X = A or B' compares X with the bitwise or of A and B; whether that was meant cannot be told from the text. None of these is reported.

```pascal
if Flags and not Mask <> 0 then  // not reported
```

### Known limits

Chains are read only in conditions of if/while/until and on the right of := - not in other call arguments (Assert(A = True or B = False)). Without evidence of the type (properties, function results, Variant) a finding stays a Warning. Generic type arguments (TList<Integer>, IsType<T>) are recognised by their shape; an unusual spelling of a comparison that looks like one ('A < B > C') is not reported as a chain.

```pascal
Assert(Ready = True or Busy = False);  // not reported
```
