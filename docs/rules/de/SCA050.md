# SCA050 — Public-Member könnte unit-private sein

![Severity](https://img.shields.io/badge/severity-Hint-blue) ![Type](https://img.shields.io/badge/type-Code%20Smell-yellow)

> Public-Member wird nur innerhalb der aktuellen Unit referenziert - Delphi-klassisches `private` (Unit-Scope) reicht

## Beschreibung

Analyse einer einzelnen Datei: das `public`-Member wird von irgendwo in derselben Unit referenziert (andere Klassen, Prozeduren auf oberster Ebene, ...), aber NICHT ausschließlich von der deklarierenden Klasse selbst. Die Verschärfung auf Delphi-klassisches `private` (das auf die Unit beschränkt ist, nicht auf die Klasse) ist sicher: jeder zulässige Aufrufer innerhalb der Unit funktioniert weiter. Dieser Detektor läuft absichtlich NUR auf einzelnen Dateien - der frühere Unit-/projektübergreifende Scan erzeugte zu viele Fehlalarme (RTTI-/DFM-Streaming, benachbarte .dpk-/.dproj-Konsumenten, generische Instanziierungen, Plugin-APIs). Der Hinweis ist eine Empfehlung; konsumiert eine fremde Unit das Member, fängt der Compiler die gebrochene Sichtbarkeit mit E2361 ab, sobald die Änderung angewendet ist. Übersprungen: published, virtual/abstract/override/dynamic, Klassenkonstruktoren/-destruktoren, RTTI-gesteuerte Basisklassen (TForm/TFrame/TDataModule/TComponent), Utility-Klassen nur aus Klassenmethoden. Zeilenweise mit `// noinspection CanBeUnitPrivate` unterdrücken, wenn die öffentliche Oberfläche beabsichtigt ist (Bibliotheks-API, Plugin-Einstiegspunkt).

## Beispiele

### Schlecht (löst die Regel aus)

> Diese Regel meldet mit niedriger Konfidenz: mit der Vorgabe `[Rules] MinConfidence=medium` bleibt das folgende Beispiel unsichtbar. Mit `[Rules] MinConfidence=low` erscheint es.

```pascal
type
  TFoo = class
  public
    procedure Helper;
  end;
  TBar = class
    procedure Run;  // calls Foo.Helper - same unit
  end;
```

### Gut (idiomatische Korrektur)

```pascal
type
  TFoo = class
  private
    procedure Helper;
  end;
// Same-unit access stays legal under Delphi-classic `private`.
```
