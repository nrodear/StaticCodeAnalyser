# SCA134 — Variable nach Free / FreeAndNil verwendet

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> Eine Variable nach `Free` oder `FreeAndNil` zu dereferenzieren liest einen hängenden Zeiger und erzeugt eine Access Violation

## Beschreibung

Nach `obj.Free` oder `FreeAndNil(obj)` zeigt die Variable auf freigegebenen Speicher (oder ist NIL). Jeder spätere Member-Zugriff, Indexer oder Aufruf mit der Variablen als Empfänger ist undefiniertes Verhalten - typischerweise eine Access Violation, manchmal stille Korruption, wenn der Speicher wiederverwendet wurde. Der Detektor entfernt Strings + Kommentare aus der Datei, findet jedes Vorkommen von `FreeAndNil(<id>)` und `<id>.Free` und durchsucht dann den restlichen Methodenrumpf vorwärts nach demselben Bezeichner. Ein folgendes `<id>.<member>`, `<id>(<args>)` oder `<id>[<idx>]` erzeugt einen Fund. Neuzuweisungen `<id> := ...` oder Anfänge eines var-Abschnitts `<id> :` beenden das Suchfenster. Bloßes Vorkommen ohne Zugriffsoperator wird absichtlich nicht gemeldet, um Fehlalarme bei Vergleichen wie `if x = oldL then` zu vermeiden. Entspricht Sonar-50-Regel #7. Einschränkung: keine Kontrollflussanalyse; `if Cond then Free else Use` kann einen Fehlalarm erzeugen, da die Verwendung auf einem anderen Pfad liegt.

## Beispiele

### Schlecht (löst die Regel aus)

> Diese Regel meldet mit niedriger Konfidenz: mit der Vorgabe `[Rules] MinConfidence=medium` bleibt das folgende Beispiel unsichtbar. Mit `[Rules] MinConfidence=low` erscheint es.

```pascal
L := TStringList.Create;
L.Free;
L.Add('x');           // <- dangling pointer
```

### Gut (idiomatische Korrektur)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  FreeAndNil(L);     // any subsequent L.Method crashes loudly
end;
```
