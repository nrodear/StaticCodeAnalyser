# SCA130 — Typecast eines Char-Werts nach PChar - Codepoint wird zur Adresse

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> `PChar('A')` ist nicht `PChar("A")` - der Typecast deutet den 16-Bit-Codepoint als rohe Speicheradresse

## Beschreibung

Delphi kompiliert anstandslos `PChar(c)`, wenn `c` vom Typ `Char`, `WideChar` oder `AnsiChar` ist. Das Ergebnis ist **kein** nullterminierter 1-Zeichen-String - der Typecast deutet den 16-Bit-/8-Bit-Codepoint einfach als Zeiger. `PChar('A')` liefert also den Zeigerwert `$00000041`, der in den unteren Prozessspeicher zeigt; jede Dereferenzierung ist undefiniertes Verhalten und endet typischerweise in einer Access Violation, liest auf manchen Plattformen aber stattdessen veraltete Daten. Gemeint ist fast immer das Muster `PChar(stringExpr)`, das einen Zeiger in den tatsächlichen String-Puffer liefert. Der Detektor durchläuft `nkCall`-Knoten, deren Name mit `PChar(`, `PWideChar(` oder `PAnsiChar(` beginnt, und meldet den Aufruf, wenn das Argument erkennbar ein Char-Wert ist: ein in Anführungszeichen gesetztes Literal aus einem Zeichen (`'A'`), ein Zeichen-Ordinal-Literal (`#65`, `#$41`) oder ein Aufruf `Chr(...)`. Bezeichner als Argumente werden nicht gemeldet, da der Detektor keinen Typ-Resolver hat, um zu bestimmen, ob die Variable ein `Char` oder ein `string` ist. Entspricht Sonar-Delphi `CharacterToCharacterPointerCastCheck`.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
var p: PChar;
p := PChar('A');           // p = $00000041 (not a string)
ShowMessage(p);              // access violation
```

### Gut (idiomatische Korrektur)

```pascal
var p: PChar;
p := PChar(string('A'));    // explicit string wrap
ShowMessage(p);
```
