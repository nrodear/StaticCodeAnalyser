# SCA207 — Nicht-ASCII-Bezeichner, den Werkzeuge zerlegen

## Beschreibung

Ein Bezeichner enthält einen Nicht-ASCII-Buchstaben - einen Umlaut, einen Buchstaben mit Akzent, einen kyrillischen oder griechischen Buchstaben. Delphi erlaubt das, doch eine Quelldatei, die als UTF-8 OHNE Byte-Order-Mark gespeichert ist, lesen die Delphi-IDE und der Delphi-Code-Formatter (Formatter.exe, Strg+D bis Delphi 12) als ANSI: Jeder Nicht-ASCII-Buchstabe wird zu zwei Zeichen, der Formatter hält das zweite für ein Satzzeichen und setzt Leerzeichen in den Bezeichner - nach dem Formatieren kompiliert die Unit nicht mehr, und die Datei ist kein gültiges UTF-8 mehr. Kommentare, String-Literale und Compiler-Direktiven übernimmt er unverändert; sie werden nicht gemeldet. Welche Buchstaben brechen, hängt von der ANSI-Codepage des Rechners ab, der formatiert (unter Windows-1252 brechen die meisten Umlaute und Buchstaben mit Akzent, das große Ü und das ß überstehen es zufällig), deshalb wird jeder Nicht-ASCII-Buchstabe gemeldet. Dateien mit BOM, UTF-16- und ANSI-Dateien werden richtig gelesen und im Delphi-Scan nicht gemeldet. Free Pascal akzeptiert nur ASCII-Bezeichner (A-Z, 0-9, Unterstrich) und bricht in jeder Kodierung mit 'illegal character' ab: Mit --dialect=fpc wird jeder solche Bezeichner als Fehler mit hoher Konfidenz gemeldet, in einer ANSI-Datei ohne den Namen (seine Buchstaben lassen sich nicht sicher dekodieren). Jeder verschiedene Bezeichner wird je Datei einmal gemeldet, an seiner ersten Stelle; inaktive {$IFDEF}-Zweige zählen mit, weil der Formatter auch sie formatiert. Behebung: die Datei als UTF-8 mit BOM speichern (Delphi) oder den Bezeichner in ASCII umbenennen (ae, oe, ue, ss) - für Free Pascal hilft nur der ASCII-Name. SCA185 meldet dasselbe fehlende BOM für die Datei als Ganzes; Doppelgänger-Buchstaben meldet SCA193.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
// file saved as UTF-8 WITHOUT BOM
var
  Groesse: Integer;  // written with o-umlaut and sharp s - the formatter inserts blanks into the name
```

### Gut (idiomatische Korrektur)

```pascal
// the same file saved as UTF-8 WITH BOM - or an ASCII name
var
  Groesse: Integer;
```

## Absichtlich nicht gemeldet

Bei den folgenden Konstrukten schweigt der Detektor absichtlich. Jedes davon ist eine False-Positive-Klasse, die am Realwelt-Korpus gemessen wurde — keine Vermutung.

### Files with a BOM, UTF-16 and ANSI files (Delphi scan)

The IDE and the formatter read these files correctly, the name stays intact. Look-alike letters in such a name are SCA193, an ANSI file as such is SCA189. With --dialect=fpc these files are reported, because Free Pascal rejects the name in every encoding.

```pascal
// UTF-8 WITH BOM
var Groesse: Integer;  // with o-umlaut - not reported in a Delphi scan
```

### Comments, string literals and compiler directives

The formatter copies them unchanged, and Free Pascal accepts non-ASCII there. Delphi-12 multi-line strings count as strings. A missing BOM for string literals is SCA185.

```pascal
// o-umlaut in a comment
S := 'o-umlaut in a string';  // not reported
```

### Characters beyond U+FFFF

A letter outside the Basic Multilingual Plane (stored as a surrogate pair) is not read as part of a name - a deliberate false negative; such identifiers do not occur in practice.

```pascal
var XY: Integer;  // with a mathematical letter U+1D400 between X and Y - not reported
```
