# SCA109 — Sperre ohne Freigabe per try/finally genommen

> TCriticalSection, Monitor oder WinAPI-Sperre ohne umschließendes try..finally genommen - eine Ausnahme lässt sie gesperrt

## Beschreibung

Eine Sperre anzufordern (TCriticalSection.Enter / .Acquire, TMonitor.Enter, TMultiReadExclusiveWriteSynchronizer.BeginWrite, WinAPI EnterCriticalSection), ohne unmittelbar ein try..finally mit dem passenden Leave / Release / EndWrite folgen zu lassen, ist einer der häufigsten Threading-Fehler in Delphi: Jede Ausnahme zwischen Anfordern und Freigeben lässt die Sperre dauerhaft gehalten und blockiert jeden späteren Aufrufer (Deadlock). Lexikalische Erkennung: findet die Anforderungsmuster und prüft, ob die nächste Anweisung nach dem `;` ein `try` ist. Für absichtlich ungeschützte Abfolgen mit `// noinspection LockWithoutTryFinally` unterdrücken (selten; bedeutet meist, dass der nächste Aufruf selbst nie eine Ausnahme auslöst).

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
FLock.Enter;
DoWork;     // exception here leaves FLock held forever
FLock.Leave;
```

### Gut (idiomatische Korrektur)

```pascal
FLock.Enter;
try
  DoWork;
finally
  FLock.Leave;
end;
```
