# SCA122 — Erneutes raise der gebundenen Exception-Variablen

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> `on E: T do ... raise E;` verwirft den ursprünglichen Stack Trace - das blanke `raise;` erhält ihn

## Beschreibung

`raise E` in einem Handler `on E: SomeException do ...` startet eine neue Ausnahme-Weitergabe, deren Ursprung die Stelle des erneuten Auslösens ist. Der ursprüngliche Stack-Trace - der Weg von der Stelle, an der die Ausnahme zuerst ausgelöst wurde, durch jede aufgerufene Routine bis zu diesem `except`-Block - ist verloren. Absturzberichte und Debugger-Ansichten zeigen dann auf den Handler, nicht auf die eigentliche Fehlerstelle, was die Triage drastisch erschwert. Gemeint war fast sicher `raise;` (ohne Argument), das das *aktuelle* Exception-Objekt mit intaktem Stack-Trace weiterreicht. Der Detektor durchläuft jeden `nkOnHandler` mit nicht leerem gebundenem Variablennamen und meldet jedes `nkRaise` in diesem Teilbaum, dessen Argument genau diese Variable ist (ohne Beachtung der Groß-/Kleinschreibung). `raise;` (ohne Argument) ist korrekt und wird nicht gemeldet; `raise EWrapper.Create(...)` wird ebenfalls akzeptiert (bewusstes Einpacken). Entspricht Sonar-Delphi `ReRaiseExceptionCheck`.

## Beispiele

### Schlecht (löst die Regel aus)

```pascal
try
  RiskyCall;
except
  on E: EDivByZero do
  begin
    Log(E.Message);
    raise E;          // loses original trace
  end;
end;
```

### Gut (idiomatische Korrektur)

```pascal
try
  RiskyCall;
except
  on E: EDivByZero do
  begin
    Log(E.Message);
    raise;            // preserves trace
  end;
end;
```
