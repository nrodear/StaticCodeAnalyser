# SCA123 — Transtypage juste avant Free / Destroy

> `TFoo(x).Free` - le transtypage ne change pas quel Destroy s'exécute (Destroy est virtuel)

## Description

Écrire `TStringList(L).Free` ou `TObject(L).Destroy` est un signe de confusion. `TObject.Free` est une enveloppe non virtuelle autour du `Destroy` *virtuel* : la répartition virtuelle passe donc par le type d'exécution de `L`, pas par le type statique du transtypage. Que l'on écrive `L.Free` ou `T(L).Free`, la même chaîne de destructeurs s'exécute. Le transtypage est donc soit redondant (transtypage vers le propre type de la variable), soit trompeur (transtypage vers une classe sans rapport qui suggère que Destroy choisira une autre redéfinition - ce ne sera pas le cas). Si la cible du transtypage est fausse, le reste du code environnant peut reposer sur cette hypothèse erronée et casser lors d'une refactorisation. Le détecteur compare `nkCall.Name` aux motifs `<Ident>(<expr>).Free[()][;]` et `<Ident>(<expr>).Destroy[()][;]` où `<Ident>` suit la convention de nommage Delphi des classes/interfaces (`T` ou `I` plus une lettre majuscule). Un simple `L.Free` et un `Owner.Bar(x).Free` qualifié (vraisemblablement un Free sur un résultat de fonction) ne sont pas signalés. Correspond à `CastAndFreeCheck` de Sonar-Delphi.

## Exemples

### Mauvais (déclenche la règle)

```pascal
procedure Cleanup(L: TObject);
begin
  TStringList(L).Free;     // cast has no effect on dispatch
end;
```

### Bon (correction idiomatique)

```pascal
procedure Cleanup(L: TObject);
begin
  L.Free;                  // virtual Destroy resolves at runtime
end;
```
