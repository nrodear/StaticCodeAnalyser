# SCA202 — not, and, or ou xor s'applique avant la comparaison

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> 'not Count > 0' ou 'A = True or B = False' - not/and/or/xor sont prioritaires sur les comparaisons, l'expression compile mais teste autre chose

## Description

En Pascal, les opérateurs not, and, or et xor sont prioritaires sur les comparaisons (=, <>, <, >, <=, >=, in) - c'est pareil en Delphi et en Free Pascal. Deux écritures compilent donc sans message et testent autre chose que ce qu'elles semblent dire. (1) 'not' devant une comparaison : 'if not List.Count > 0' est '(not List.Count) > 0'. Pour un entier, not est le complément bit à bit, donc la condition est fausse pour tout Count >= 0 ; 'not Key in [...]' et 'not Result = mrOk' échouent de la même façon. (2) Comparaisons enchaînées par and/or/xor : 'if A = True or B = False' est '(A = (True or B)) = False'. Cela ne compile que si les opérandes sont Boolean (ou Variant) - avec des entiers, des chaînes, des énumérations ou des ensembles, le compilateur signale déjà une erreur de type. Mettre la comparaison entre parenthèses : 'not (List.Count > 0)', '(A = True) or (B = False)' - ou supprimer la comparaison avec True/False. La sévérité est Erreur quand le type est établi (un nombre ou un ensemble de nombres à droite, Pos/Ord/Length/CompareText... ou .Count/.IndexOf comme opérande, une variable locale, un paramètre ou un champ de type entier, True/False dans la chaîne) et Avertissement sinon. Sont lus les conditions de if/while/until/case et les membres droits de := ; les commentaires, les littéraux de chaîne (y compris les chaînes multilignes de Delphi 12) et les blocs asm ne comptent jamais comme du code.

## Exemples

### Mauvais (déclenche la règle)

```pascal
if not List.Count > 0 then   // (not List.Count) > 0 - false for every Count
  Exit;
if Ready = True or Busy = False then   // (Ready = (True or Busy)) = False
  Start;
```

### Bon (correction idiomatique)

```pascal
if not (List.Count > 0) then
  Exit;
if Ready or not Busy then
  Start;
```

## Volontairement non signalé

Le détecteur garde volontairement le silence sur les constructions ci-dessous. Chacune est une classe de faux positifs mesurée sur le corpus réel — ce n'est pas une supposition.

### Boolean operand with = or <>

For Boolean values (not A) = B is the same as not (A = B), so the order does not change the result. Not reported when True/False stands on the right, when the operand ends in a well-known Boolean member (Checked, Visible, Enabled, Active, ReadOnly, Modified, Focused, Showing, Eof, Bof, IsEmpty, Selected, Expanded, Down), or when the operand or the identifier on the right is a variable, parameter or field of a Boolean type. With <, >, <=, >= or in the order would matter for Booleans too - such code is practically never written and is not reported (deliberate false negative).

```pascal
if not CheckBox1.Checked = Ini.ReadBool('a', 'b', False) then  // not reported
```

### Bit tests and open intent

'Flags and Mask = 0' is '(Flags and Mask) = 0' - the correct bit test. 'not' behind and/or/* is part of the operand ('Flags and not Mask <> 0' clears bits before the test). 'X = A or B' compares X with the bitwise or of A and B; whether that was meant cannot be told from the text. None of these is reported.

```pascal
if Flags and not Mask <> 0 then  // not reported
```

### Known limits

Chains are read only in conditions of if/while/until and on the right of := - not in other call arguments (Assert(A = True or B = False)). Without evidence of the type (properties, function results, Variant) a finding stays a Warning. Generic type arguments (TList<Integer>, IsType<T>) are recognised by their shape; an unusual spelling of a comparison that looks like one ('A < B > C') is not reported as a chain.

```pascal
Assert(Ready = True or Busy = False);  // not reported
```
