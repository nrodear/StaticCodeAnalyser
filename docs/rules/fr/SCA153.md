# SCA153 — Paire Lock/Unlock sans try/finally

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> Lock / EnterCriticalSection / TMonitor.Enter avec sa libération dans la même routine mais sans try/finally - le chemin d'exception laisse le verrou posé et bloque l'appelant suivant

## Description

Analyse lexicalement chaque ligne source (commentaires + chaînes retirés) à la recherche du jeton de prise `<ident>.Lock`, `Acquire`, `EnterCriticalSection` ou d'un `EnterCriticalSection(...)` nu. Une fenêtre d'anticipation d'au plus 200 caractères - tronquée au début de la routine suivante - cherche ensuite le jeton de libération correspondant (`UnLock`, `LeaveCriticalSection`, `Release`) ; une libération qui appartient à une méthode voisine (façade Lock/UnLock, paire Begin/End, garde de portée constructeur/destructeur) ne compte plus. Quand les DEUX sont présents dans la fenêtre mais qu'aucun mot-clé `try` ne précède la libération, la paire est signalée - prendre un verrou puis lever une exception avant la libération provoque un interblocage pour chaque attente ultérieure. Ajusté pour mORMot : reconnaît TSynLocker, TRWLock, TLightLock et la paire Windows nue EnterCriticalSection/LeaveCriticalSection. Les motifs où la libération manque entièrement sont ignorés (probablement un style RAII avec un assistant de verrou dont la libération se trouve dans un destructeur).

## Exemples

### Mauvais (déclenche la règle)

```pascal
FLocker.Lock;
DoStuff;
FLocker.UnLock;
```

### Bon (correction idiomatique)

```pascal
FLocker.Lock;
try
  DoStuff;
finally
  FLocker.UnLock;
end;
```
