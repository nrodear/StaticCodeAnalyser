# SCA207 — Identificateur non-ASCII que les outils cassent

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> Identificateur avec des lettres non-ASCII dans un fichier UTF-8 sans BOM (le formateur Delphi le coupe) ou sous Free Pascal (ne compile pas)

## Description

Un identificateur contient une lettre non-ASCII - un umlaut, une lettre accentuée, une lettre cyrillique ou grecque. Delphi l'accepte, mais un fichier source enregistré en UTF-8 SANS marque d'ordre des octets (BOM) est lu comme de l'ANSI par l'IDE Delphi et par le formateur de code Delphi (Formatter.exe, Ctrl+D jusqu'à Delphi 12) : chaque lettre non-ASCII devient deux caractères, le formateur prend le second pour un signe de ponctuation et insère des espaces dans l'identificateur - après le formatage, l'unité ne compile plus et le fichier n'est plus de l'UTF-8 valide. Les commentaires, les littéraux de chaîne et les directives de compilation sont recopiés tels quels et ne sont pas signalés. Les lettres qui cassent dépendent de la page de codes ANSI de la machine qui formate (en Windows-1252, la plupart des umlauts et des lettres accentuées cassent, le Ü majuscule et le ß survivent par hasard) ; c'est pourquoi toute lettre non-ASCII est signalée. Les fichiers avec BOM, les fichiers UTF-16 et ANSI sont lus correctement et ne sont pas signalés dans une analyse Delphi. Free Pascal n'accepte que des identificateurs ASCII (A-Z, 0-9, souligné) et s'arrête avec 'illegal character' dans tout encodage : avec --dialect=fpc, chaque identificateur de ce type est signalé comme erreur avec une confiance élevée, dans un fichier ANSI sans le nom (ses lettres ne se décodent pas de façon sûre). Chaque identificateur distinct est signalé une fois par fichier, à sa première occurrence ; les branches {$IFDEF} inactives comptent, car le formateur les formate aussi. Correction : enregistrer le fichier en UTF-8 avec BOM (Delphi) ou renommer l'identificateur en ASCII (ae, oe, ue, ss) - pour Free Pascal, seul le nom ASCII aide. SCA185 signale le même BOM manquant pour le fichier dans son ensemble ; les lettres sosies relèvent de SCA193.

## Exemples

### Mauvais (déclenche la règle)

```pascal
// file saved as UTF-8 WITHOUT BOM
var
  Groesse: Integer;  // written with o-umlaut and sharp s - the formatter inserts blanks into the name
```

### Bon (correction idiomatique)

```pascal
// the same file saved as UTF-8 WITH BOM - or an ASCII name
var
  Groesse: Integer;
```

## Volontairement non signalé

Le détecteur garde volontairement le silence sur les constructions ci-dessous. Chacune est une classe de faux positifs mesurée sur le corpus réel — ce n'est pas une supposition.

### Files with a BOM, UTF-16 and ANSI files (Delphi scan)

The IDE and the formatter read these files correctly, the name stays intact. Look-alike letters in such a name are SCA193, an ANSI file as such is SCA189. With --dialect=fpc these files are reported, because Free Pascal rejects the name in every encoding.

```pascal
// UTF-8 WITH BOM
var Groesse: Integer;  // with o-umlaut - not reported in a Delphi scan
```

### Comments, string literals and compiler directives

The formatter copies them unchanged, and Free Pascal accepts non-ASCII there. Delphi-12 multi-line strings count as strings. A missing BOM for string literals is SCA185.

```pascal
// o-umlaut in a comment
S := 'o-umlaut in a string';  // not reported
```

### Characters beyond U+FFFF

A letter outside the Basic Multilingual Plane (stored as a surrogate pair) is not read as part of a name - a deliberate false negative; such identifiers do not occur in practice.

```pascal
var XY: Integer;  // with a mathematical letter U+1D400 between X and Y - not reported
```
