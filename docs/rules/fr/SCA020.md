## Description

Une méthode vide peut indiquer une implémentation oubliée, un TODO jamais traité ou un stub d'interface. Rendre l'intention explicite (assert, exception ou commentaire). Non signalé : un corps vide qui porte déjà un commentaire explicatif ({ do nothing }, // default implementation does nothing) - ce commentaire *est* l'une des trois corrections que demande la règle. Ne comptent pas comme intention : les directives de compilation ({$REGION}, {$IFDEF}) et le code commenté (reconnu au point-virgule final). Cela n'affaiblit pas la règle du projet selon laquelle les commentaires ne comptent jamais comme *utilisation* de code - la question ici est l'intention documentée, pas l'utilisation.

## Exemples

### Mauvais (déclenche la règle)

```pascal
procedure DoStuff;
begin
end;
```

### Bon (correction idiomatique)

```pascal
procedure DoStuff;
begin
  raise ENotImplemented.Create('...');
end;
```

## Volontairement non signalé

Le détecteur garde volontairement le silence sur les constructions ci-dessous. Chacune est une classe de faux positifs mesurée sur le corpus réel — ce n'est pas une supposition.

### Empty body carrying an explanatory comment

The rule's own advice is to make the intent explicit by assert, exception *or comment*. A body that already carries a comment has followed that advice, so reporting it contradicts the fix the rule asks for. Two things do NOT count as intent: a compiler directive (`{$REGION}`, `{$IFDEF}`) is tooling rather than a statement about intent, and commented-out code - recognised by the trailing semicolon - documents nothing. Note this does not weaken the project rule that comments never count as code *usage*; the question here is documented intent, not use.

```pascal
// not reported - the intent is stated
procedure TFoo.DoNothing;
begin
  { do nothing - base class hook }
end;

// still reported - nothing says why
procedure TFoo.DoNothing;
begin
end;
```
