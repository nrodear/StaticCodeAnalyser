# SCA177 — Variable de thread utilisee après FreeOnTerminate := True

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> Après T.FreeOnTerminate := True, tout accès ultérieur à T.Field/T.Method risque une Access Violation si le thread s'est déjà auto-détruit

## Description

TThread.FreeOnTerminate := True transfère la possession de l'instance de thread au thread lui-même - le thread libère sa propre mémoire dans son cycle de vie Execute-puis-Destroy. L'appelant DOIT abandonner immédiatement toutes ses références au thread (en général en mettant la variable locale à nil), car il n'existe aucune synchronisation entre l'instruction suivante de l'appelant et l'autodestruction du thread. Le détecteur parcourt chaque méthode, collecte chaque affectation `<var>.FreeOnTerminate := True`, puis le premier `<var>.Start` ou `<var>.Resume` - à partir de ce moment, le thread tourne et peut se libérer lui-même - et signale chaque accès `<var>.<member>` ultérieur (appel OU affectation) dans la même méthode, à l'exception des appels de cycle de vie Start, Resume et Execute. Sans Start ni Resume dans la méthode, rien n'est signalé. Portée par méthode : les références entre méthodes (thread détenu dans un champ et utilisé dans une autre méthode) ne sont pas suivies.

## Exemples

### Mauvais (déclenche la règle)

```pascal
T := TMyThread.Create(True);
T.FreeOnTerminate := True;
T.Start;
T.WaitFor;   // T may already be freed -> AV
```

### Bon (correction idiomatique)

```pascal
T := TMyThread.Create(True);
T.FreeOnTerminate := True;
T.Start;
T := nil;   // drop the reference
```
