# SCA160 — Transtypage en chaîne depuis un pointeur brut

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> `string(P)` et variantes depuis un pointeur préfixe P supposent un terminateur nul qui peut ne pas exister - lecture au-delà du tas

## Description

Analyse lexicale de `(string|RawByteString|AnsiString|UTF8String|WideString)(<id>)` où `<id>` commence par `P` suivi d'une autre lettre (convention Delphi du préfixe P pour les types pointeur : PByte, PChar, PSomeRecord, ...). La correspondance ignore la casse, donc `pText` correspond aussi ; un opérande déclaré avec un type chaîne dans le même fichier est ignoré. Delphi traite le transtypage comme terminé par un nul et lit la mémoire jusqu'au prochain #0 - sur un tampon sans terminateur, la lecture dépasse la limite du bloc de tas, ce qui provoque une lecture hors limites silencieuse et parfois une AV. Le code interne de mORMot utilise ce motif avec une terminaison nulle maîtrisée ; le code utilisateur qui copie l'idiome omet souvent la garantie du terminateur. Utiliser plutôt `SetString(s, PChar(Buf), Len)` avec une longueur explicite. Filtre anti-faux positifs : seuls les identificateurs commençant par P déclenchent - `string(IntegerVar)` (Integer vers String) n'est pas signalé ; un double transtypage comme `string(PChar(x))` ne l'est pas non plus.

## Exemples

### Mauvais (déclenche la règle)

```pascal
PText := PChar(Buf);
s := string(PText);   // reads up to the next #0 - overread if Buf has no terminator
```

### Bon (correction idiomatique)

```pascal
SetString(s, PChar(Buf), Len);   // explicit length, no terminator needed
```
