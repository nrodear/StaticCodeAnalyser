# SCA139 — Free sans mise à nil ensuite

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Code%20Smell-yellow)

> `obj.Free;` sans `obj := nil;` (ni FreeAndNil) laisse un pointeur pendant - toute utilisation ultérieure est un Use-After-Free

## Description

> Cette section n'existe qu'en anglais. Le nom et la description courte sont traduits ; les textes complets suivent la version anglaise.

After `obj.Free`, the variable still points at the freed memory. Any further dereference is Use-After-Free, an Access Violation at best, silent corruption at worst. The detector walks `nkCall` nodes whose name matches `<ident>.Free` or `<ident>.Destroy`, then forward-scans the same method for a subsequent `<ident> := nil` or `FreeAndNil(<ident>)`. If neither exists, the call is reported - in a method also when it is the last call: a field outlives the method, and a later `Assigned` check or the destructor touches freed memory (in a constructor Delphi runs the destructor on every exception). A standalone routine that frees a global as its last call (cleanup at program or script end) is not reported unless a `raise` follows. Local variables, inline constants and parameters are skipped (they go out of scope), destructors, `BeforeDestruction` and OnDestroy handlers too (the instance dies with them). `Self`/`Result`/`inherited` as receivers are excluded since they follow different lifecycle patterns. Maps to Sonar-50 rule #25.

## Exemples

### Mauvais (déclenche la règle)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  L.Free;             // <- L still points at freed memory
end;
WriteLn(L.Count);     // Use-After-Free
```

### Bon (correction idiomatique)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  FreeAndNil(L);      // L is nil; further use raises loudly
end;
```
