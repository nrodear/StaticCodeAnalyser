# SCA134 — Variable utilisée après Free / FreeAndNil

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> Déréférencer une variable après `Free` ou `FreeAndNil` lit un pointeur pendant et provoque une violation d'accès

## Description

Après `obj.Free` ou `FreeAndNil(obj)`, la variable pointe vers de la mémoire libérée (ou vaut NIL). Tout accès ultérieur à un membre, à un indexeur ou tout appel utilisant la variable comme receveur est un comportement indéfini - typiquement une violation d'accès, parfois une corruption silencieuse si la mémoire a été réutilisée. Le détecteur retire chaînes + commentaires du fichier, trouve chaque occurrence de `FreeAndNil(<id>)` et `<id>.Free`, puis parcourt vers l'avant le reste du corps de la méthode à la recherche du même identificateur. Un `<id>.<member>`, `<id>(<args>)` ou `<id>[<idx>]` ultérieur produit un résultat. Les réaffectations `<id> := ...` ou les débuts de section var `<id> :` terminent la fenêtre d'analyse. Les apparitions nues sans accesseur ne sont volontairement pas signalées, pour éviter les faux positifs sur des comparaisons comme `if x = oldL then`. Correspond à la règle Sonar-50 #7. Limite : pas d'analyse de flot de contrôle ; `if Cond then Free else Use` peut produire un faux positif, car l'utilisation se trouve sur un autre chemin.

## Exemples

### Mauvais (déclenche la règle)

> Cette règle signale avec une confiance faible : avec la valeur par défaut `[Rules] MinConfidence=medium`, l'exemple ci-dessous reste masqué. Avec `[Rules] MinConfidence=low`, il apparaît.

```pascal
L := TStringList.Create;
L.Free;
L.Add('x');           // <- dangling pointer
```

### Bon (correction idiomatique)

```pascal
L := TStringList.Create;
try
  L.Add('x');
finally
  FreeAndNil(L);     // any subsequent L.Method crashes loudly
end;
```
