# SCA130 — Transtypage d'un Char en PChar : le point de code devient une adresse

![Severity](https://img.shields.io/badge/severity-Error-red) ![Type](https://img.shields.io/badge/type-Bug-red)

> `PChar('A')` n'est pas `PChar("A")` - le transtypage traite le point de code 16 bits comme une adresse mémoire brute

## Description

Delphi compile sans broncher `PChar(c)` où `c` est de type `Char`, `WideChar` ou `AnsiChar`. Le résultat n'est **pas** une chaîne d'un caractère terminée par un nul - le transtypage réinterprète simplement le point de code 16 bits/8 bits comme un pointeur. Ainsi `PChar('A')` renvoie la valeur de pointeur `$00000041`, qui pointe dans la mémoire basse du processus ; tout déréférencement est un comportement indéfini et se termine généralement par une violation d'accès, mais sur certaines plateformes lit plutôt des données périmées. Le motif voulu est presque toujours `PChar(stringExpr)`, qui renvoie un pointeur dans le tampon réel de la chaîne. Le détecteur parcourt les nœuds `nkCall` dont le nom commence par `PChar(`, `PWideChar(` ou `PAnsiChar(` et signale l'appel quand l'argument est reconnaissable comme une valeur Char : un littéral entre apostrophes d'un seul caractère (`'A'`), un littéral ordinal de caractère (`#65`, `#$41`), ou un appel `Chr(...)`. Les arguments identificateurs ne sont pas signalés, car le détecteur n'a pas de résolveur de types pour déterminer si la variable est un `Char` ou une `string`. Correspond à `CharacterToCharacterPointerCastCheck` de Sonar-Delphi.

## Exemples

### Mauvais (déclenche la règle)

```pascal
var p: PChar;
p := PChar('A');           // p = $00000041 (not a string)
ShowMessage(p);              // access violation
```

### Bon (correction idiomatique)

```pascal
var p: PChar;
p := PChar(string('A'));    // explicit string wrap
ShowMessage(p);
```
