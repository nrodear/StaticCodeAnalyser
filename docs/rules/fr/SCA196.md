# SCA196 — Result de type managé est lu avant d'avoir été affecté

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> Le Result d'un type de retour managé est lu avant la première affectation - il est un alias de la variable cible de l'appelant et porte son ANCIENNE valeur. L'initialiser d'abord (nil / [] / '')

## Description

Pour les types de retour managés, le compilateur passe Result comme paramètre var caché, alias de la variable cible de l'appelant, Y COMPRIS son contenu précédent (System.Rtti UseResultPointer ; la RTL elle-même s'en protège, p. ex. TStringBuilder.ToString commence par Result := '' 'to prevent copying of existing data'). Result n'est donc PAS initialisé à ''/nil/vide à l'entrée. Le lire avant la première affectation - Result := Result + [x], Result[i] := ... sans SetLength préalable, Result.Add(...), Exit(Result + ...) - traite des données périmées de l'appelant : le symptôme classique est une fonction collectrice dont le second appel ajoute aux résultats du premier. Le conseil du compilateur W1035 (valeur de retour indéfinie) reste MUET précisément pour ces types, donc rien d'autre n'avertit ici. La détection suit purement l'ordre du source (variante 2, sans analyse de chemins) : le premier accès à Result dans le corps décide ; tout ce qui écrit ou peut écrire Result (affectation directe, Exit(value), Result ou @Result passé comme argument d'appel, comme SetLength(Result, n) ou TryGetValue(key, Result)) compte comme affectation et termine l'examen. Les fonctions avec un alias 'absolute Result', les routines assembleur et les déclarations sans corps sont ignorées ; les littéraux de chaîne contenant le mot 'result' ne comptent jamais. Aveugle aux chemins par conception : une écriture dans une branche suivie d'une lecture après la branche n'est PAS signalée (faux négatif, pas faux positif) - une analyse sensible aux chemins est une suite prévue. L'alias de résultat par le nom de la fonction compte UNIQUEMENT comme cible d'affectation : dans un contexte d'expression, un nom de fonction nu est toujours un APPEL (récursif/sans paramètre) - 'Result := Put;' invoque la surcharge sans paramètre et ne lit jamais Result ; 'Obj.Result' est un champ étranger. Les affectations jumelles sous IFDEF, les méthodes anonymes incorporées (dont le Result appartient à la fonction anonyme) et les idiomes de remplissage de tampon 'Result[0] := Char(Api(@Result[1], N))' sont traités comme des écritures, pas comme des lectures. Pour les résultats ShortString, 'Result[0] := #len' est l'idiome d'initialisation de l'octet de longueur et compte comme première écriture. Là où cette règle se déclenche, SCA121 reste muette pour la même fonction.

## Exemples

### Mauvais (déclenche la règle)

```pascal
function CollectNames(const L: TStrings): TArray<string>;
var i: Integer;
begin
  for i := 0 to L.Count - 1 do
    Result := Result + [L[i]];  // reads the CALLER's old array on first iteration
end;
```

### Bon (correction idiomatique)

```pascal
function CollectNames(const L: TStrings): TArray<string>;
var i: Integer;
begin
  Result := [];  // or: Result := nil; / SetLength(Result, 0);
  for i := 0 to L.Count - 1 do
    Result := Result + [L[i]];
end;
```

## Volontairement non signalé

Le détecteur garde volontairement le silence sur les constructions ci-dessous. Chacune est une classe de faux positifs mesurée sur le corpus réel — ce n'est pas une supposition.

### Result or @Result passed as a call argument

SetLength(Result, n), TryGetValue(key, Result), FillChar(Result, ...) and friends write through the var/out parameter - lexically we cannot tell read from write, so every argument pass counts as initialization (conservative, same direction as SCA121).

```pascal
SetLength(Result, Count);  // counts as the first write
```

### Local variable declared 'absolute Result'

All writes go through the alias name; the walker would never see a Result write and would flag every alias-based initializer.

```pascal
var Bits: UInt32 absolute Result;
```

### assembler routines and bodyless declarations

asm bodies set the result via registers; abstract/forward/external/dispid declarations have no body to scan.

### Write in one branch, read after the branch

Variant 2 is path-blind by design: the read is only flagged when NO write precedes it in source order - a branch-guarded miss is a false negative, never a false positive. Path-sensitive analysis (CFG) is a planned follow-up.

### Record and class return types

Record field writes are legitimate partial initialization, and for class-typed results the compiler hint W1035 already warns; both stay out of scope.

### Function name in expression context

In a Delphi expression a bare function name is always a (recursive/parameterless) CALL - the result alias exists only as an assignment target left of ':='. 'Result := Put;' invokes the parameterless overload, 'Result := Obj.GetTitle' calls another object's method, 'Result := inherited GetAsString' calls the parent. Reads are therefore only ever detected through the identifier 'Result' itself.

```pascal
function TClient.Put(const Res: string): IResponse; begin ...; Result := Put; end;  // calls Put()
```

### 'Obj.Result' - a field of another object

A dotted prefix means the identifier belongs to another symbol (e.g. task.Result); it never aliases the local Result.

### ShortString: Result[0] := #len

For ShortString results the length byte IS the initialization (classic idiom before Move into Result[1]); element writes on ShortString count as the first write.

```pascal
function Pack(B: Byte): ShortString; begin Result[0] := AnsiChar(1); Result[1] := AnsiChar(B); end;
```

### mormot TDynArray and ALL-CAPS I* types

TDynArray is a record wrapper (Result.Init(...) is legitimate initialization) despite the *DynArray name; ICONMETRICS-style ALL-CAPS names are Windows API records, not interfaces - both are excluded from the return-type gate.

### Parse artefacts: IFDEF twins, anonymous methods, @Result buffer fills

A second 'result := ...' appearing inside an assignment's right-hand side is an IFDEF-twin parse artefact (both preprocessor branches kept) and counts as a write; a right-hand side containing an embedded anonymous method is never counted as a read (its Result belongs to the anonymous function); 'Result[0] := Char(Api(@Result[1], N))' passes @Result to the API which fills the buffer - a write, not a read.
