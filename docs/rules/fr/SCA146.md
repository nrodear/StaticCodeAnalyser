# SCA146 — Paramètre booléen servant d'aiguillage interne

![Severity](https://img.shields.io/badge/severity-Hint-blue) ![Type](https://img.shields.io/badge/type-Code%20Smell-yellow)

> Un paramètre booléen dont la valeur choisit entre deux chemins de code complètement différents est une stratégie déguisée - préférer deux méthodes aux noms parlants

## Description

Quand la valeur d'un paramètre booléen fait basculer la fonction entre deux comportements sans rapport (`SendMsg(s, True)` vs `SendMsg(s, False)`), le site d'appel est opaque : le lecteur doit soit se souvenir de l'API de la méthode, soit la consulter pour savoir ce que signifie `True`. Deux méthodes aux noms parlants (`SendErrorMessage` / `SendInfoMessage`) rendent l'intention évidente au site d'appel sans commentaires. Le détecteur parcourt les nœuds `nkMethod`, examine les enfants `nkParam` de type Boolean (ainsi que LongBool/WordBool/ByteBool) et signale dès qu'au moins un `nkIfStmt` du corps utilise le paramètre comme condition. Exclus : setters de propriété (noms de méthode commençant par `Set`), noms de paramètres bien connus de gestionnaires d'événements VCL (`Handled`, `CanShow`). Le simple relais (booléen seulement transmis, sans branchement interne) n'est pas signalé. Correspond à la règle Sonar-50 #33. Sévérité Conseil - il s'agit d'une suggestion de refactorisation, pas d'un bug.

## Exemples

### Mauvais (déclenche la règle)

```pascal
procedure SendNotification(const Msg: string; IsError: Boolean);
begin
  if IsError then Notify(Msg, clRed) else Notify(Msg, clBlack);
end;
// Caller: SendNotification(s, True);     // True = ???
```

### Bon (correction idiomatique)

```pascal
procedure SendErrorNotification(const Msg: string);
begin Notify(Msg, clRed); end;

procedure SendInfoNotification(const Msg: string);
begin Notify(Msg, clBlack); end;
// Caller: SendErrorNotification(s);
```
