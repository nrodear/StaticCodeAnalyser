# SCA156 — GetMem / AllocMem sans try/finally

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> GetMem / AllocMem / ReallocMem suivi du FreeMem correspondant dans la même routine mais sans try/finally englobant - le chemin d'exception perd le tampon définitivement

## Description

Analyse lexicale (commentaires + chaînes retirés) à la recherche de `GetMem(...)`, `AllocMem(...)` ou `ReallocMem(...)`. Une fenêtre d'anticipation de 400 caractères cherche le `FreeMem` correspondant. Quand les deux sont présents dans la fenêtre mais qu'aucun mot-clé `try` ne précède le FreeMem, la paire est signalée - toute exception entre l'allocation et la libération fait fuir le tampon brut du tas. Ajusté pour mORMot : reconnaît les ~20 occurrences de GetMem dans core/ de mORMot qui implémentent une manipulation de tampons haute performance, où chaque try/finally manquant est une fuite en production. Les motifs où FreeMem manque entièrement sont ignorés (probablement transfert de propriété vers l'appelant, ou allocateur personnalisé).

## Exemples

### Mauvais (déclenche la règle)

```pascal
GetMem(P, 1024);
DoStuff(P);
FreeMem(P);
```

### Bon (correction idiomatique)

```pascal
GetMem(P, 1024);
try
  DoStuff(P);
finally
  FreeMem(P);
end;
```
