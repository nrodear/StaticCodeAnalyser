# SCA122 — Relevée de la variable d'exception liée

![Severity](https://img.shields.io/badge/severity-Warning-orange) ![Type](https://img.shields.io/badge/type-Bug-red)

> `on E: T do ... raise E;` perd la pile d'appels d'origine - le `raise;` nu la conserve

## Métadonnées

| Champ | Valeur |

| **Kind** | `ReRaiseException` |
| **Sévérité par défaut** | Warning |

## Description

`raise E` dans un gestionnaire `on E: SomeException do ...` démarre une nouvelle propagation d'exception enracinée au site de la relance. La pile d'appels d'origine - le chemin depuis l'endroit où l'exception a été levée la première fois, à travers chaque routine appelée, jusqu'à ce bloc `except` - est perdue. Les rapports de plantage et les vues du débogueur pointent alors vers le gestionnaire, et non vers l'emplacement réel de la faute, ce qui rend le tri considérablement plus difficile. L'intention du développeur était presque certainement `raise;` (sans argument), qui continue de propager l'objet exception *courant* avec sa trace intacte. Le détecteur parcourt chaque `nkOnHandler` ayant un nom de variable liée non vide et signale chaque `nkRaise` de ce sous-arbre dont l'argument est exactement cette variable (insensible à la casse). `raise;` (sans argument) est correct et n'est pas signalé ; `raise EWrapper.Create(...)` est également accepté (encapsulation délibérée). Correspond à `ReRaiseExceptionCheck` de Sonar-Delphi.

## Exemples

### Mauvais (déclenche la règle)

```pascal
try
  RiskyCall;
except
  on E: EDivByZero do
  begin
    Log(E.Message);
    raise E;          // loses original trace
  end;
end;
```

### Bon (correction idiomatique)

```pascal
try
  RiskyCall;
except
  on E: EDivByZero do
  begin
    Log(E.Message);
    raise;            // preserves trace
  end;
end;
```
