# Release 0.9.18 — Error means proven, a baseline that holds, and one findings report

🇩🇪 [Deutsche Fassung](v0.9.18_de.md)

Three long-running efforts land together: an evidence policy that makes
the error tier trustworthy, a baseline whose entries can no longer
silence half a scan, and a findings report that was rebuilt around the
person who has to read it. Around them, the largest false-positive pass
the rule set has had — over thirty rules report less, none of them
because a threshold was loosened.

---

## Error means proven

Finding severity is now capped by the detector's confidence in that
*specific* finding: only high-confidence findings appear at `error`,
medium reports at `warning` at most, low at `hint`. On the reference
corpus this cuts the error-tier false-positive rate from ~32 % to ~4 %.

The consequences are deliberate:

- **Breaking for CI gates** that count on the old error totals —
  `--fail-on error` no longer fails on capped findings. That is the
  point. Opt out with `[Rules] EvidenceTiering=0` in `analyser.ini`.
- SARIF results carry `properties.confidence` while the policy is
  active, so a consumer can see *why* a catalog-error rule reports at
  `warning`. The state is stamped at scan time and travels with the
  finding cohort — toggling the ini between scan and export cannot mix
  two policy states.
- Rules whose audits could not support their confidence were demoted
  (SCA001 MemoryLeak, SCA008 NilDeref, SCA173, SCA086); findings of
  SCA121 and SCA109 that pass all source gates were re-promoted to the
  error tier — 136 verified true positives returned.

## The engine parses what the compiler compiles

Single-branch `{$IFDEF}` view and include-define tracking are now the
defaults: inactive conditional branches are skipped (defines
`MSWINDOWS,WIN64,UNICODE,CONDITIONALEXPRESSIONS`), and `{$I}` include
files are read for their `{$DEFINE}` effect — libraries that keep their
symbols in include files (mORMot, Indy, JVCL) are seen the way the
compiler sees them. ~15,000 double-branch phantom findings disappear
from the reference corpus. Opt-outs: `--no-ifdef-aware`,
`--no-include-defines`, `--define X[,Y]`.

## A baseline that holds

Four repairs, one theme — a baseline entry should match exactly the
finding it accepted, nothing more and nothing less:

- The GUI and the IDE plugin now match on the **context hash** as well,
  the either/or rule the CLI has applied since v0.9.8. Re-tuning a
  metric threshold no longer resurfaces 37,987 findings whose code
  never moved.
- The context-hash key now **carries file and rule**. Before, any entry
  suppressed every finding in the scan whose seven-line window was
  textually identical — measured worst case: one entry could silence
  38.6 % of the corpus, most of it in *other files*. Now 6.1 % with
  `[Baseline] PathInFingerprint=1`, 27.4 % without (the bare-name
  residue the legacy fingerprint always had).
- The **score and threshold of the four metric rules** (SCA012, SCA018,
  SCA022, SCA176) are no longer part of the fingerprint, so tuning
  `CyclomaticMax` no longer changes the identity of every finding of
  that rule. SCA018 also stops writing the *line number* into its
  message — the entire rule used to lose its baseline assignment on a
  pure line shift.
- `--write-baseline` writes **valid JSON**. Delphi's pretty printer
  passes raw control characters through; three entries out of 783,104
  made all 371 MB unreadable for `jq`, `python json.load` and
  `JSON.parse`. Our own tolerant readers were never affected — no gate
  went wrongly green. And the HTML report's "load baseline" button no
  longer swallows a parse error silently.

**What you will see:** findings can now *appear* that a baseline used
to hide — nothing is hidden that was not hidden before. Flipping
`PathInFingerprint` invalidates context-hash matching; `--baseline`
says so in its mismatch warning.

## One findings report, half the size

Next to the original HTML report the GUI's export menu had gained a
second, workbench-based one — and a third variant existed briefly
during development, distinguished only by a version number in the
caption. What
remains is the **workbench report**: health rating, stat tiles and two
top lists first, then search, file and rule dropdowns and
type/severity/confidence chips, then the findings table. A click on a
finding opens a side drawer with the source excerpt, the location and
the documentation of exactly that rule. Page header, filter bar and
column row pin below one another while the page scrolls — and there is
deliberately only *one* scroller, so the page scrolls until the pinned
parts latch.

It is roughly **half the size** it used to be, for a reason worth
naming: the rule documentation is stored once per rule instead of once
per finding, the source excerpt ships as raw text (the scaffolding is
built in the browser when the drawer opens, character-identical to
before), and the search reads the visible row instead of carrying a
lowercased copy of it. About 990 bytes saved per finding, computed from the emitted markup.

Smaller things that matter at a desk: the default file name carries the
date (`sca_codereview_YYYY-MM-DD.html`), form controls are readable in
the dark theme, and the stored theme is applied before first paint —
no flash.

Alongside it, the **detector info export** writes a self-contained rule
catalog: all 198 rules with documentation, before/after examples, CWE,
config key and detector unit, sortable and searchable.

The CLI's `--report-html` is a different, unchanged report —
[EXPORTS.md](../../EXPORTS.md) explains which serves what.

## Rules that stopped claiming what they could not prove

The first full false-positive audit of the rule set (142 active rules,
3,162 verdicts read at source) turned into a round of fixes, and later
audits kept feeding it. A selection: SCA003 (SQLInjection) learned six
safe-pattern conventions from a 96 % false-positive autopsy; SCA008
(NilDeref) gained five gates; SCA017 stops flagging file I/O as debug
output; SCA025 respects runtime DFM translators; SCA086 respects ABI
directives; SCA089 rebuilt its section tracking; SCA118 evaluates the
direct base class only. Each fix removed a claim the rule could not
support — no thresholds were loosened.

The parser no longer swallows the `else` of a `case` whose last arm
ends in an `if` — statements that had been invisible to every rule
returned to the syntax tree. And a generated C-binding header no longer
produces 806 naming findings in a single file.

Measured across the passes, the upper bound on the strict profile's
false-positive rate fell **below 2 %** for the first time.

## CLI hardening

A value on a boolean switch is now a **parse error**: `--full=false`
used to switch `--full` **on** — the value was silently dropped, and
the caller got the exact opposite of what they wrote. And a CLI started
without a console (service, task scheduler, GUI parent) no longer dies
on its first output line: both standard streams are always bound — to
their redirect, the console, or the null device.

## Also in this release

Rule-set **profiles** you can shape and import; two new rules about
interface GUIDs — SCA197 flags an interface without one, SCA198 finds
the same GUID on two interfaces, which compiles cleanly and hands back
the wrong interface at run time; and the filter dropdown no longer
freezes after the first mouse selection.

## Migration

- CI gates counting error totals: read the evidence-tiering entry
  above; opt out with `[Rules] EvidenceTiering=0` if you need time.
- Baselines: nothing to migrate. Baselines older than v0.9.8 carry no
  context hash — findings of the four metric rules surface once as
  new there; re-write the baseline.
- Sonar export drops downgraded findings by default —
  `--sonar-keep-downgraded` keeps them.
