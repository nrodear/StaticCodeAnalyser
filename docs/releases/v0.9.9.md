# Release 0.9.9 — Fewer false positives, two project-scope rules

**Released:** 2026-08-02
🇩🇪 [Deutsche Version](v0.9.9_de.md)

This cycle had one dominant theme: **the tool reports less, and what it
reports is worth reading.** On the 12,800-file reference corpus the finding
count fell from **645,622 to 560,964 — 84,658 fewer findings (−13.1 %)**,
with no true positive knowingly lost. Alongside that, the rule roster grew
from 183 to **195 rules** (`SCA001`–`SCA195`).

If you are upgrading from 0.9.3 or earlier, note that the CHANGELOG now
also documents v0.9.5, v0.9.6 and v0.9.7, which had been released without
release notes. **There is no version 0.9.4** — it was skipped.

---

## TL;DR

- **−84,658 findings on the reference corpus (−13.1 %).** Seven increments,
  each measured and gated separately.
- **Two new rules, `SCA194` and `SCA195`,** covering a class of defect no
  single-file check can see: files that are not part of the project, and
  units the project compiles without listing.
- **Rule pages now say what a rule deliberately does *not* report.**
- **The CLI states its active rule set on every run.** Previously it stayed
  silent when the profile came from `analyser.ini`.
- **The version number is no longer duplicated in the source.** In 0.9.8 a
  second hard-coded copy would have kept `--version` on the old number.

## Why 84,658 findings disappeared

A false positive costs more than the second it takes to read. It teaches
the reader that this rule is noise, and the next finding from the same rule
gets skipped too — including the real one. The campaign therefore targeted
the rules that produced the most output, not the ones that were easiest to
change.

Every increment was built on its own branch, measured in a single corpus
run against the previous baseline, and only released once the *dropped*
findings had been sampled to confirm they were not defects. Each increment
had to hold three anchors: **zero added findings**, no movement in any rule
outside the increment, and no unintended movement in the error tier.

| Increment | Rules | Effect |
|---|---|---|
| Ownership transfer via `out` parameters | `SCA001` | −493 |
| Hint-tier gates | `SCA155`, `SCA073`, `SCA147`, `SCA080` | −17,577 |
| Declaration & reference visibility | `SCA119`, `SCA132`, `SCA020`, `SCA053`, `SCA164` | −10,531 |
| Duplicate reporting & interface contracts | `SCA106`, `SCA070`, `SCA054`, `SCA001` | −20,455 |
| Parser: attributes in parameter position | `SCA054`, `SCA013` | −41 |
| Declaration boilerplate | `SCA021` | −3,403 |
  | **One finding per duplicated block** | `SCA021` | **−32,158** |

The recurring pattern: a rule must not fire where the language *forces* the
repetition, or where a call simply is not visible by name. Message handlers
and interface implementations are dispatched without the method ever being
named. A published-property list or a parameter list cannot be extracted
into a shared method, so reporting it as a duplicate block asks for
something impossible. And a declaration plus its implementation is one
identifier and one rename — not two findings.

### Changes you will notice in day-to-day use

- **`SCA080 RedundantJump` no longer looks at `Break`.** This one was
  actively harmful. Unlike `Continue`, a `Break` at the end of a loop body
  suppresses the remaining iterations — following the old hint turned
  search loops into full scans and `while True` loops into infinite ones.
  `Break` is only genuinely redundant in `repeat … Break; until True`,
  which does not occur once in the reference corpus.
- **`SCA106 MethodName` reports a badly named method once,** not once for
  the declaration and once for the implementation. Same-named methods in
  *different* classes are still reported separately.
- **`SCA020 EmptyMethod` accepts an intent comment.** The rule's own advice
  is to make the intent explicit through an assertion, an exception *or a
  comment*; a body carrying `{ do nothing — base class hook }` has already
  followed it. Compiler directives and commented-out code do not count.
- **`SCA132 ExceptionTooGeneral` accepts a handler that forwards the
  exception** to logging or rethrow logic instead of swallowing it.

## `SCA194` and `SCA195` — project membership

Both rules need a view that no single-file check has: the set of files on
disk and the set of units actually reached by `uses`, compared against what
the project file lists. They therefore only run in a project or
project-group scan, not in a plain directory scan.

- **`SCA194 NotIncludedInProject`** — a `.pas`/`.dfm` lies in the project
  tree, but no `.dproj`/`.groupproj` references it. Usually a leftover that
  is still edited, still turns up in searches, and is never compiled.
- **`SCA195 UsedButNotInProject`** — the mirror case, and the more
  dangerous one. The unit *is* pulled in via `uses` and compiles through
  the search path, but is missing from the project file. It builds on the
  machine where the path happens to be configured and fails everywhere
  else, which makes it a classic "works on my machine" defect. Resolution
  follows `uses` transitively from the `.dpr` root and walks **both**
  branches of an `{$IFDEF}`: a unit used only in the currently inactive
  branch is still a member of the project.

## Documentation: what a rule does *not* report

After a false-positive campaign the most common question is not "why did
this fire?" but the opposite: *"is this case handled, or did the rule just
miss it?"* Nothing in the documentation could answer that.

The rule catalogue gained an optional `exceptions` field — case, mechanism,
and an optional snippet — and every rule page now renders a **"Not reported
(by design)"** section from it. Deliberate false negatives are documented
the same way, so that a design decision is not mistaken for a bug years
later.

`tools/gen-rules-docs.py` now also validates the catalogue against its own
JSON schema when `jsonschema` is installed (`--no-schema-check` opts out).
The schema had shipped since 1.0 but had never actually been executed
against the catalogue; the first run found a `shortDescription` of 208
characters against a documented limit of 200.

## The CLI tells you which rules ran

The `Rule-set:` line used to appear **only** when `--profile` or
`--min-severity` was passed explicitly. If the profile came from
`analyser.ini`, the CLI said nothing about it.

That silence is expensive. A `Profile=ide-fast` in the INI yields zero
findings for every hint-tier rule, and the only evidence the caller gets is
an empty result list — which looks exactly like a broken build. During
development this cost a full misdiagnosis before anyone thought to look at
the INI.

The line is now printed on every run (unless `--quiet`), and it names both
the origin of each setting and the resulting rule count:

```
Rule-set: Profile=strict (analyser.ini), MinSeverity=hint (analyser.ini/Default), 195 rules active
```

## Findings can span more than one line

A `DuplicateBlock` is a **block**. It was reported as a single line, and the
reader had to guess where the duplication ended — hopeless for a 20-line
block.

### `SCA021` reports one finding per duplicated block

The sliding window walks the block line by line, and every position is a
different hash that reported at its own start line. A K-line duplication
therefore produced **K−7 findings stacked on top of each other**. The guard
that was supposed to prevent this keyed on the start line — which is unique
per window — so it could never fire, while the unit header claimed the
opposite. In the reference corpus one class declaration carried **18 hints
on top of each other**.

Windows of the *same* duplication are now merged into one finding covering
the whole block: **41,306 → 9,148 findings (−32,158)**, with no other rule
moving at all.

"Same duplication" is decided by the **occurrence signature** — the
distances between the copies — not by line overlap. As the window slides
through one block, all its copies shift by the same amount, so the
distances stay constant; a different set of distances means a different
duplication. Merging purely by line overlap would have hidden one group's
partner site entirely and mis-reported multiplicity: measured on one file,
five merged runs mixed distinct groups, the worst announcing "appears 2x"
for a run containing a 10×-duplicated block.

### The editor marks the whole range

Every line of the block carries the stripe, so the extent is visible at a
glance. The continuation lines are **not findings**: no badge, no hover
overlay, no entry in any list. The finding stays anchored at its first
line, and the findings list still shows one entry — clicking dismiss
removes the whole range.

SARIF gained `region.endLine` for multi-line findings; its absence means
single-line, as the format specifies.

### Migration note

If you silenced one of these cascades with **line-bound**
`// noinspection DuplicateBlock` comments, the markers on the swallowed
lines are no longer consumed and will surface as `SCA165 UnusedSuppression`.
A single marker on the block's first line replaces them. File-wide
`// noinspection-file` markers are unaffected.

## Searchable rule filter, and a clearer duplicate marker

**The rule filter is now searchable.** The combo labelled *Severity* does
not hold three entries but roughly two hundred — every rule as
`SCAxxx  KindName`, grouped by section. Scrolling that is the wrong way to
use it. Type `sqlinj` and `SCA003` comes up: characters have to occur in
order but need not be adjacent, and matches at word starts and CamelCase
boundaries rank first. Empty input restores the full list, Escape discards
the query, and the filter is applied when the list closes — not while you
arrow through it. Available in both the standalone app and the IDE plugin.

**Duplicate blocks are marked as blocks.** The stripe in the editor now
spans every line of the duplication and carries a bracket: a cap on the
first line, one on the last. The continuation lines are **not** findings —
no badge, no hover card, no entry in the list. Where two duplications
overlap, only one of them draws the bracket; both keep their anchor and
their info bar, so nothing disappears from the report. Roughly a quarter
of all `SCA021` findings overlap another one, so without that rule the
stripes would stack into an unreadable column.

The standalone app's filter combo was widened to match the plugin.

### Known behaviour, not a defect

While you type in the filter combo, Windows hides the mouse pointer and
brings it back on the next mouse movement. That is the system setting
*Pointer Options → Hide pointer while typing*, which applies to every
Windows text field — the path combo and the search box behave the same
way. It can be switched off in Mouse Properties.

### Performance: `SCA166 UninitVar` was quadratic in file size

The rule spent a full-file scan **per candidate variable**: it checked
whether the variable's name is also declared as a type in the file, and
that check walked every line of the unit. The comment at the call site
claimed it ran "only for the few emit candidates" — it did not. The gates
above it do not yet decide whether anything is reported; that is decided
below. An ordinary write-then-read local paid a complete file scan and
reported nothing. Since the number of locals grows with file size, the
cost was quadratic in it.

The call now sits in the two emit branches, immediately before the
finding. Measured on the reference corpus, against unchanged detectors to
factor out machine variance:

| | before | after |
|---|---|---|
| `UninitVar` share of detector CPU | **36.9 %** | **7.9 %** |
| per file | 8.43 ms | 0.73 ms |
| rank among 150 detectors | 1 | 3 |

Attributable to the fix: **−86 %** of the rule's own time. Findings are
byte-identical — all 141 rules unchanged on the corpus.

### `SCA021` message names the real line range

The message said `Code block (8 lines)` while the editor marked a larger
region. The eight counted *normalised* lines — blank lines and comments
removed — whereas the marked region counts source lines, so the two could
never agree. It now reads:

```
Code block (lines 513-533, 8 matched lines) appears 2x in file
```

**Migration:** the SARIF fingerprint is a hash over rule + path + line +
**message**, so every `SCA021` finding gets a new fingerprint and will
appear once as *new* in existing baselines. Re-write the baseline after
updating (`--write-baseline`). No other rule is affected, and the number of
findings does not change.

## Fixed

- **Attributes in parameter position produced phantom parameters.** For
  `procedure Post(const [MVCFromBody] P: TPerson)` the parser emitted a
  second `nkParam` named after the attribute. Sixteen rules read `nkParam`;
  visibly, `SCA054` reported the attribute name as an unused parameter and
  `SCA013` both over- and under-counted parameters.
- **The regex cache grew without bound in the IDE plugin.** The cache key
  assumed pool threads are reused — true for the CLI, but the plugin's
  bulk-scan worker starts fresh threads per scan whose ids never come back,
  while their compiled regex instances stayed. Now capped.
- **The size guard for an external `.po` file came too late** — the file
  was fully loaded and only then compared against the limit. The size now
  decides before a single byte is copied.
- **An embedded translation was never selected for a language code that
  differed in case.** The generated dispatcher compared case-sensitively
  while the caller normalises, so a `PT.po` would have been ignored,
  falling back to English without any error.
- **`i18n_extract.py` harvested constants out of expressions.** Any
  `NAME = <literal>` counted, including comparisons mid-expression, so
  `Found := Ext = '.pas';` produced a "constant" named `Ext`.
- **The version number was hard-coded twice.** `uConsoleRunner` carried its
  own `SCA_VERSION` copy that shadowed the one in `uSCAConsts` — which
  documents itself as the single source of truth. A bump there alone would
  have left `--version`, the banner and the SARIF tool block on 0.9.8.

## Self-scan

The tool is run against its own source as a release gate. All thirteen
error-tier findings are gone: ten were test fixtures that carry the
anti-pattern on purpose, and three were false positives of our own rules —
which is the good news in that number, since it means the tool finds no
actual defect in itself. All are suppressed with a stated reason, and the
three false-positive classes are recorded as detector work for a later
cycle.
