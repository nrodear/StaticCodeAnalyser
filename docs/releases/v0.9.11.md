# Release 0.9.11 — Repairs

**Released:** 2026-08-03
🇩🇪 [Deutsche Version](v0.9.11_de.md)

A fix release, one day after 0.9.10. No new rules, no new features.
Everything here is one of three things: a false positive proven on the
reference corpus, a regression that crept in with 0.9.10, or a version number
that had quietly stopped being true.

---

## TL;DR

- **Scrolling in the IDE plugin is quick again** — three causes, all
  introduced or amplified by the multi-line marking in 0.9.10.
- **`SCA028` no longer reports two kinds of non-finding**: an event
  explicitly cleared with `nil`, and a handler that only *seems* missing
  because the ancestor class name was ambiguous.
- **`SCA054` asks the source before claiming a parameter is never read.**
- **`SCA099 IfElseBegin`** joins the `style` profile — it belonged with the
  other six all along.
- **The plugin no longer calls itself v0.9.8.**

---

## Scrolling in the plugin

The complaint was simply that it had got worse. It had, and the reason is a
combination rather than a single mistake.

**The gutter bracket asks for every line.** `PaintLine` checks whether a line
is marked at all and leaves immediately if not. `PaintGutter`, added in
0.9.10, went straight to the lookup — so every visible line started paying,
marked or not.

**Continuation lines are marks now.** Since findings cover whole blocks, a
`DuplicateBlock` over 21 lines turns one marked line into twenty-one. Marked
lines run the expensive branch, so in a duplicate-heavy file nearly every
visible line carries the full cost. That part is the feature working as
intended — but it multiplied everything else.

**Every scroll event forced a full repaint.** `EditorScrolled` invalidated
all lines immediately, on top of the repaint the editor performs anyway, and
one mouse-wheel notch delivers several scroll events. The call is necessary:
the editor *blits* the lines it moves, so the per-line callback never fires
for them and the hit-test cache would stay incomplete. It is now coalesced
through a 90 ms settle timer that fires once, when the movement stops.

Path normalisation was three string allocations per call and ran several
times per visible line; it is memoised now.

## The findings grid painted every cell twice

The renderer draws background, selection highlight and text itself — for the
header as well as the cells. But `DefaultDrawing` was never switched off, so
the grid painted each cell in full first and the renderer painted over it.
At six columns and fifty visible rows that is roughly 300 redundant cell
paints per frame. The panel grid had it right from the beginning; the main
grid was the outlier.

## `SCA028` — two kinds of non-finding

**An event bound to `nil` is not a missing handler.** `OnCustomDrawItem = nil`
says the opposite: the event is deliberately cleared. It was collected as a
binding anyway. Filtered at the source, because four detectors share that
event list and none of them wants a `nil` binding.

**An ancestor resolved from an ambiguous name proves nothing.**
`TfrmSplashScreen` inherits from `TfrmBase` — and skia4delphi carries
`TfrmBase` *twice*, once under `Samples/Demo/VCL` and once under `.../FMX`.
Only the VCL one declares the handler. The class index kept the first hit and
dropped the rest silently, so the VCL form was bound against the FMX base and
the handler merely *appeared* to be missing.

The index now records which class names live in more than one unit, the
binder marks bindings reached through such a name, and the rule stays quiet
for them. A chain can run formally all the way up to a framework root and
still be a stranger's.

> **A known limit, deliberately not patched over:** a property whose name
> starts with `On` need not be an event. `TJvUIBQuery.OnError = etmStayIn`
> assigns an *enum*, not a method. In DFM text the two are indistinguishable
> — both are bare identifiers — and a heuristic over spelling is out, because
> enum literals (`etmStayIn`) and IDE-generated handlers (`btnOkClick`) have
> exactly the same shape. Such a gate would take most of the real findings
> with it.

## `SCA054` — asking the source before claiming absence

The body this rule counts against is assembled from the name and type text of
AST nodes. That is a *lossy* approximation of the source: the index
expression on the left of an assignment and the arguments behind an `as` cast
never appear in it. Both reproduced on the built analyser —
`SystemPath[Kind] := 'x'` reported `Kind` as unused, `(Obj as TOther).M(Index, 1)`
reported `Index`.

Before claiming a parameter is never read, the rule now asks the source,
exactly as it has done since 2026-07-18 for routines the parser discards.
Strings and comments are stripped first: a name that appears only in a
comment is still not a use, and there is a test for precisely that.

The check can only *remove* findings, never add any.

## `SCA099 IfElseBegin` → `style`

The analysis behind the profile split named **seven** pure-convention rules;
0.9.10 shipped with six. `IfElseBegin` — asymmetric `begin..end` between the
`if` and the `else` branch — was left behind for no stated reason. It is the
same shape as `BeginEndRequired`, which did move: a Code Smell at Hint
severity about how the source is written, not about what it does.

On the reference corpus it is **14,982 findings, 2.7 %**, so `default` now
shows 4.9 % less than before. `style` covers exactly the seven; `strict` is
unaffected.

## Version numbers that had stopped being true

The IDE plugin announced itself as **v0.9.8** in its window title —
hardcoded, two releases behind. The installer script carried the same stale
number.

**Six places carry the version**, not four: the two constants in
`uSCAConsts`, the rule catalogue's `tool.version`, the two `.dproj` version
blocks, the plugin title and the installer. They are now listed in the
installer script, so the next bump has them in one place.

---

## Upgrading

Nothing to do. No rule changed its behaviour in a way that alters a
fingerprint, and no baseline needs rewriting. If you rely on `SCA099` being
part of `default`, switch to `--profile strict` or add `--profile style` as a
second run.
