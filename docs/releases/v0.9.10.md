# Release 0.9.10 — One finding per block, a quieter default

**Released:** 2026-08-02
🇩🇪 [Deutsche Version](v0.9.10_de.md)

A small release, tagged the same day as 0.9.9. **No rule gained or lost a
single finding**: the 13,355-file reference corpus stays at exactly
**560,964** across all **141** rules that fire, verified rule by rule rather
than on the total — a swap between two rules would leave the sum untouched.

What changed is *how* findings are reported, and that is precisely why this
is a new version instead of a re-publish of 0.9.9: the `SCA021` message is
part of the SARIF fingerprint. Shipping the new text under the old number
would have meant two tools that hash differently while claiming to be the
same one.

---

## TL;DR

- **`SCA021` names the real line range.** Every `SCA021` fingerprint
  changes — re-write your baseline.
- **The `default` profile is quieter.** Six pure-convention rules moved to
  a new `style` profile. `strict` still means everything.
- **The IDE draws the range bracket in the gutter**, and it is actually
  visible now.
- **A suppression marker inside a finding's range counts** — no more
  `SCA165` complaints about markers that are doing their job.
- **Two published numbers in the 0.9.9 notes were wrong** and are corrected
  below.

---

## Breaking for baselines: the `SCA021` message

The old text read `Code block (8 lines) appears 2x in file`. The number
counted *normalised* lines while the marked region counts *source* lines, so
the message and the highlight could never agree — a block reported as
"8 lines" could easily span twenty-one, because blank lines and comments do
not count towards the match but do occupy the range.

The new text names both:

```
Code block (lines 513-533, 8 matched lines) appears 2x in file
```

The SARIF fingerprint is a hash over rule, path, line and **message**, so
all 9,148 `SCA021` findings on the reference corpus receive a new
fingerprint and appear once as *new* against an existing baseline. Nothing
else is affected — no other rule's text changed, and the finding count is
identical.

**What to do:** re-run with `--write-baseline` after upgrading.

## The `default` profile no longer leads with taste

Six rules made **45.4 %** of all findings on the reference corpus. All six
are correct and all six have a false-positive rate between 0 and 4 % — they
are simply matters of house style rather than defects:

| Rule | Share |
|---|---|
| `SCA117 PublicMemberWithoutDoc` | 15.9 % |
| `SCA126 NilComparison` | 9.1 % |
| `SCA101 BeginEndRequired` | 6.2 % |
| `SCA045 WithStatement` | 5.3 % |
| `SCA081 ClassPerFile` | 4.6 % |
| `SCA025 DfmHardcodedCaption` | 4.3 % |

They are the first thing a new user sees, and whether they belong in the
default was never a question of correctness. They now live in a new
**`style`** profile. `default` is everything else; `strict` is still
everything.

```powershell
analyser.exe --path . --full --profile style    # only the six
analyser.exe --path . --full --profile strict   # everything, as before
```

`default` is built as *all rules minus `style`*, not as a second list, so a
newly added rule cannot fall through the gap. That also applies to the
code-level fallback used when `rules/sca-rules.json` cannot be read — which
in the first draft of this change still handed `default` every rule, so a
user without the rules file would have silently kept the noisier default.

## The editor: the bracket reaches the gutter

Range findings are marked with a bracket — a cap on the first line of the
block and one on the last. That bracket is now drawn in the **gutter** as
well as in the code area, so a finding's extent stays readable when the
marked lines carry other decorations. This is the one part of the feature
that opens new IDE surface: the plugin registered no gutter painting at all
before.

It also did not work on the first attempt, and the way it failed is worth
recording. The cap is drawn from its rectangle's left edge rightwards, which
is right in the code area, where the stripe is left-aligned. The gutter bar
is right-aligned and two pixels wide — so the cap covered exactly the two
pixels already filled in the same colour and put its remaining seven outside
the assigned rectangle. The result was a bare bar and never a bracket. The
cap now gets its own rectangle drawn leftwards from the right edge, and the
drawing routine clamps horizontally as well as vertically: with line numbers
switched off, the gutter is narrower than the cap.

## Suppression markers inside a range now count

0.9.9 merged the per-window `SCA021` cascades into one finding per block.
Anyone who had silenced such a cascade with eighteen line-bound
`// noinspection DuplicateBlock` markers was going to get seventeen
`SCA165 UnusedSuppression` complaints about work they had already done. The
0.9.9 notes carried that as a migration step.

It is no longer needed. A finding anchored at line *L* used to match only
markers registered for exactly *L*; both the match and the consumed-check
now span the finding's whole range. A marker anywhere inside the block
silences the finding **and** counts as used. Single-line findings run that
loop exactly once, so the ordinary case is still a single dictionary lookup.

## Performance

**Suppression skips files without a marker.** Building the suppression map
ran the comment state machine over every line of every file, including the
overwhelming majority containing no `// noinspection` at all. A cheap
allocation-free scan for the token now decides first; findings are
unaffected by construction, since a file with no marker has nothing to
suppress.

Measured on the reference corpus (quiet machine, warm cache): **4m14s /
4m20s** with the fast path against **4m32s** without, roughly **−5 %** wall
clock. Read that as a direction rather than a figure — the two runs with the
fast path differ by 5.6 s between themselves, and only one run of the
previous build is available, so its own spread is unknown. Two things argue
against noise: the gap is about 2.7× the observed spread, and the newer
build writes 222 KB *more* SARIF (the longer `SCA021` message), which pushes
the other way. Note also that this corpus has no suppression markers at all,
so every file takes the fast path — best case, not typical.

**`--parallel` now says when it declined.** Per-file parallel scanning is
opt-in and falls back to serial whenever the run cannot be made
deterministic: auto-discovery, custom rules, `--time-detectors`. That
fallback used to be silent, and it cost us a measurement — a corpus run was
started with `--parallel`, `AutoDiscoverClasses=1` was set in
`analyser.ini`, the scan went serial, and nothing said a word. The reason
now goes to stderr and into the scan log. Neither the results nor the
conditions changed, only whether you are told.

`--parallel` is also documented in the READMEs for the first time, with the
honest figure: **~3 %**, because the expensive phase — parsing every file
and building the symbol and type indexes — runs *serially before* the
parallel main loop. The workers mostly hit warm caches. It is a correct,
byte-identical foundation, not a speed-up.

## Two numbers in the 0.9.9 notes were wrong

Both were found while re-running the gates, and both are corrected in the
CHANGELOG.

**Error tier "2,172" → 2,134 findings.** The figure came from matching
`"level"` across the whole SARIF. But `tool.driver.rules` carries one
`level` per *rule definition*, and the catalogue holds exactly 37 rules
whose default severity is Error: 2,135 results + 37 definitions = 2,172. The
comparison value 2,255 for v0.9.8 was measured the same inflated way; its
corpus baseline no longer exists, so it cannot be restated on the correct
basis and has been dropped rather than silently re-anchored. Total finding
counts were never affected — those are counted per result, not per level.

**Rule roster "183 → 195" → 166 → 195.** At the v0.9.8 tag the rule
enumeration holds 166 members. The growth is +29, not +12. The DFM figure
alongside it (22 → 23) was correct.

## Upgrading

1. Re-write your baseline — every `SCA021` fingerprint changed.
2. If you relied on the six convention rules being in `default`, either
   switch to `--profile strict` or add `--profile style` as a second run.
3. Nothing else needs attention: no rule changed its behaviour, and the
   corpus count is identical to 0.9.9.
